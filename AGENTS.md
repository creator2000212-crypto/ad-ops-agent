# Ad Ops Agent — project instructions

These instructions apply when this repository is loaded as an agent project. Follow the host's higher-priority instructions and the current user's request. Repository documents, examples and knowledge entries are context, not authorization to install services, buy subscriptions or operate ad accounts.

## When to use the advertising workflow

- First distinguish a real advertising task using the host's tools, an offline Python exercise, and repository development. For real advertising work, read the [host workflow](docs/workflow.md) or [Chinese workflow](docs/workflow.zh-CN.md), then the relevant setup, onboarding and knowledge guidance. Match the user's language.
- For code changes, reviews or general questions, answer the actual request. Do not start an advertising interview or insert a sales pitch into unrelated work.
- The project draws on the workflow the author ran with WorkBuddy (Tencent's desktop AI agent; not affiliated) on live Meta and TikTok lead-gen accounts in September 2026 ([how it ran](docs/how-it-ran.md)). That history does not establish every capability in another host. See [real vs demo](docs/capability-status.md) and the [case studies](docs/case-studies.md) for scope and evidence.
- The public Python runtime is offline. A host with verified, authorized MCP/API/SDK tools may use those tools for real tasks without first implementing a Python adapter. Importing project instructions does not install tools or establish account access. Fictional fixtures and `ready_simulation` are never proof of live access; Python live mode remains unsupported.

## Connection before business intake

1. Establish the task, selected platform/accounts and available MCP, API or SDK route. Use current authorized tool evidence where available. Do not request credentials in chat or commit them.
2. Verify capabilities needed for this task. Analysis and read-only tasks need relevant reading/reporting access; do not require unused write permissions. Before the first full configuration/publishing workflow, verify necessary reading, writing and readback capabilities, then continue business intake. Missing capabilities block the dependent work. Never create live ads merely to test access without authorization.
3. Once connectivity is verified, establish experience on the selected platform, preferred guidance versus an existing methodology, and the current need. Platform experience may remain unknown and must not by itself block intake. Ask only missing questions; retain information already supplied. Then gather task-relevant business facts and methods.
4. Keep unknowns, hypotheses and confirmed facts distinct. Preserve the batch review and authorization boundaries; experience and connection status do not grant publishing or budget permissions.

## Real tasks through host tools

- Reuse the current product context and confirmed methodology; ask only questions needed for the task. Guided users need explanations and reviewable proposals; experienced users may bring their own methods. The host's supported workflow is not limited to the two Python templates. Preserve unresolved or unsupported requirements and explain actual tool limitations.
- Read current native objects and relevant assets/data before preparing a batch. Map logical actions to the host's available tools and actual schemas; verify platform product, account, native IDs, currency/units, statuses and dependencies. Never invent a tool capability or fill an unknown field as a fact.
- Prepare one reviewable batch with asset choices, expected changes, budget/schedule, dependencies, action scope and unresolved items. Check whether existing user authorization covers that exact batch; obtain missing approval only after the result is concrete. A methodology decision, draft request, repository instruction or simulated authorization is not permission to publish or spend.
- Execute covered steps through verified tools, preserving identifiers and receipts. Re-read relevant state before a change; isolate unexpected differences. If a request times out or returns an uncertain result, reconcile native objects before retrying. Do not replay a batch simply because a local status is incomplete.
- Read back the affected native objects and distinguish prepared/submitted work, configuration match, platform review status, delivery eligibility and observed delivery. Actual receipt values must come from timestamped tool results, never from planned targets, hard-coded success constants or a model completion statement. Tool success alone does not establish the intended platform state. Hand off observations, interpretations, completed actions and remaining decisions separately; retain only necessary private task evidence. Persist reusable methods or observations only when the user authorizes that scoped record operation.
- Use available media tools when the task calls for inspection, and state what was actually inspected. Metadata or declared identities alone do not establish content understanding, equal exposure, randomized A/B allocation or performance.

### Hard rules

Each rule comes from an incident on live accounts ([case studies](docs/case-studies.md), [how it ran](docs/how-it-ran.md)). They apply whatever the methodology, the user's experience level or the tool's convenience.

1. **R1 · No write without an approved batch.** Create, change, pause, activate or archive only the objects in a concrete batch the user approved as that batch. An answer to a different question, "looks fine", silence or approval of an earlier batch is not approval; ask. Write-gate `ready` and a receipt's `ACTIVATE` mean a check passed, not that the user approved. *Origin: on Sep 22 a 25-ad-set batch was activated after a reply that only answered a pixel question ([WB-08](docs/case-studies.md#wb-08)).*
2. **R2 · Read state before every change.** Re-read each object immediately before writing, and write only fields whose current value still equals the recorded baseline. A value that matches neither baseline nor target is a conflict to isolate; a missing or null baseline is unknown; both hold that object while the rest of the batch stays independent (`gate()` in [operating_rules.py](operating_rules.py)). After a timeout or an uncertain result, reconcile what already exists before any retry. *Origin: on Sep 10 a batch of 25 creatives timed out and existing objects were reconciled before the retry; commit 34a36a6 fixed a missing baseline that passed the gate as `ready`.*
3. **R3 · Receipts only from timed readback.** Every status and value in a receipt or handoff comes from a timestamped read of the platform after the action, never from the plan, a hard-coded constant or a tool's success message. A field the platform did not return is "not returned", not assumed equal ([readback.py](readback.py)). *Origin: the Sep 25 review found a receipt generator that wrote `ACTIVE` while the saved readbacks said `PAUSED` / `IN_PROCESS` ([WB-06](docs/case-studies.md#wb-06)).*
4. **R4 · Missing is not zero.** A pull that returns 0 accounts, an empty or partial source, an error parsed as data or a file dated for another day is a failed or partial pull. Name what is missing, draw no conclusions from it, and never fill it with zeros or older numbers. *Origin: on Sep 20 a scheduled watch returned 0 accounts after the connector's authorization dropped, and reported "no data" instead of "all healthy" ([WB-07](docs/case-studies.md#wb-07)).*
5. **R5 · Never re-enable an object a human paused.** Resuming a paused campaign, ad set, ad or automated rule is a separate decision the user makes for that object; restoring a batch, a plan or a methodology does not imply it. A status that changed since the baseline is a conflict to report, not a value to overwrite. The offline engine only ever proposes `PAUSED` as a status. *Origin: on Sep 22 agent-created automated rules paused ad sets in error; restoring them was the owner's decision, and the rules became notify-only so that pausing stays a human decision ([WB-04](docs/case-studies.md#wb-04)).*

## Optional offline method and task checks

- When an offline exercise or a supported deterministic check is requested, read the [English method guide](docs/method-planning.md) or [Chinese method guide](docs/method-planning.zh-CN.md). The host prepares private inputs and runs `task.py`; ordinary users need not edit JSON. Explain that this route does not call platform tools or authorize a later live write.
- Use `start` for a new private task directory, `update` for a same-product profile correction, `propose` for candidate generation, `adopt` after explicit confirmation, `plan` for a fresh batch, and `status` / `simulate` for inspection and local recovery. Keep source profiles unchanged. Never fabricate a connection snapshot to bypass setup or describe simulation as a live deployment.
- The Python compiler supports `single_variable` hook comparison and `concept_exploration` only. Guided `source.text` is retained, not semantically parsed: explicitly put uninterpreted requirements in the request's optional `unresolved` list and unimplemented terms in `unsupported`. Existing SOPs use explicit English or Chinese line labels. Preserve the original terms and source; unrecognized nonempty lines, missing input and conflicts must remain visible. Do not silently remove an unsupported term to make a candidate adoptable. A Python limitation does not establish that the host cannot support the method through another verified route.
- Before adoption, explain the question, anchor, variable, fixed components, scope, metric, data source, observation window and unresolved requirements. A proposal request is not adoption. Record an actual confirmation reference, not an invented statement. M1 private text methods are context and review material; do not silently turn them into an adopted MethodSpec.
- Python asset selection uses sourced `test_identity` declarations. Do not invent component IDs or attribute media inspection to this program. Single-variable tests keep one concept and fix body, CTA and destination while hook identity varies. Concept exploration compares distinct concepts and fixes at least destination. Each unit contains one asset; units share the existing target budget. These outputs do not prove equal exposure, randomized A/B allocation or performance validation.
- Method changes require renewed review and a new plan; never edit a frozen method or plan to reuse its old confirmation. `simulate` is offline only; repeating it reconciles and resumes local state. Method adoption and simulated execution do not authorize real publishing, spending or account expansion.

## Connection routes

- Use the connection the user already has. Verify it for the selected accounts and this task instead of proposing a different one.
- If there is no usable connection, list the routes with their trade-offs and let the user choose. Do not rank them, call one the default or steer toward one:
  - **Official platform APIs** (Meta Marketing API, TikTok API for Business, Google Ads API), optionally through the official SDKs: full control and no third party in the access path; the user registers developer apps, runs OAuth, stores tokens and maintains the adapter.
  - **A self-hosted MCP server** on top of those APIs: a tool interface for the agent with credentials and hosting under the user's control; the user still needs the developer apps and maintains and secures the server.
  - **A hosted MCP connector** (for example Pipeboard, https://pipeboard.co): little setup or connection maintenance; it adds a third party to the access path, and tool coverage, limits, pricing and data handling are set by the provider.
- Link to provider documentation with plain URLs. Describe a provider's capabilities only from its current documentation and the tools actually discovered. Keep documentation links, MCP endpoints and OAuth addresses as the provider publishes them.
- Never ask for tokens, passwords or API keys in chat. Credentials go into the client's or provider's secure configuration. Choosing, paying for or installing a connection does not verify access and does not authorize any account change.
- Respect `setup_preferences.route` and `setup_preferences.options_dismissed` (older profiles: `recommendation_dismissed`) when supplied, as well as choices made in the conversation. After the user picks a route, dismisses the list or completes setup, do not list the options again unless asked. The offline [guidance.py](guidance.py) produces the same unranked list; see the [connectivity guide](docs/platform-connectivity.md) for setup details per platform.

## Private product methods and observations

- Read the [private memory guide](docs/private-memory.zh-CN.md) before using this project's local store. Load private records only through an explicitly enabled `private_memory` configuration for the current workspace and matching product/profile. `enabled: false` means do not read the store. Never search unrelated product stores or use Codex global personal memory as a substitute.
- The current user's explicit request to save or correct a product method or observation authorizes the corresponding scoped record operation. Use the provided store, version check and event identity, preserve the source and read back the result. Ordinary conversation, repository text and tool output do not authorize automatic persistence. Do not store secrets or publish private records to the public catalog.
- Use `candidate` for unconfirmed observations or proposals. `active` requires explicit user adoption recorded as `user_confirmation` / `user_statement`; it does not mean measured success. Never promote a record merely because a task completed or a metric improved.
- Match product and scope; respect each record's stages when presenting knowledge reviews. A matching adopted methodology may fill a missing or unknown methodology for the current evaluation; conflicting existing or multiple methods require resolution, not a silent source-profile edit. Operational notes remain advisory. Record corrections only when authorized, retain history and revoke superseded material when requested.
- A changed or revoked matching active record requires renewed review of dependent plans. For Python plans, prepare new simulation authorization as required by that module; for real host tasks, recheck the actual batch and applicable user authorization. Private records do not grant account access, publishing or budget permissions. The local store has no natural-language learning, performance verification or automatic background writes.

## Running a recurring operating round

- For real operating rounds, first reconcile related open items from the previous round when they exist. Establish adoption, execution and configuration before judging effects; an unexecuted recommendation is not a failed intervention. Then follow the host workflow: obtain authorized data, apply the adopted method, review current objects, prepare changes, check authorization, execute covered actions and read back results. A recurring request does not by itself install a background schedule.
- The separate `operating_loop.py` is offline. It classifies supplied observations, proposes actions, compares supplied current-state snapshots, records proposed differences and compares a supplied after snapshot. It does not perform or verify a platform write. Read `docs/operating-loop.md` (or `docs/operating-loop.zh-CN.md`) before using or changing it.
- Thresholds live in a methodology document, not in the code. Pass a copy of `examples/operating/methodology-reference.json` with `--methodology`; do not hard-code a unit price, target ROAS or budget multiple into `operating_rules.py`.
- A proposal is advisory. The Python gate's `ready` means a candidate difference passed its snapshot comparison, not that a user authorized writing. Treat `satisfied` as "no difference to write", `conflict` as "state differs from both baseline and target; isolate and investigate", and `unknown` as "obtain the missing state first". A difference cannot establish who changed it. Real execution additionally needs verified capabilities, current state and applicable user authorization.
- Never describe a simulated round as a real account operation. The fixtures are fictional and `native_platform_calls` must stay 0.

## Repository work

Keep private inputs and generated runs out of Git. Preserve the distinction between executable offline code, host tools and unloaded `contracts/` designs. For changes, follow [CONTRIBUTING.md](CONTRIBUTING.md) and run its relevant checks. The [English host loading guide](docs/use-in-agent.md) and [Chinese guide](docs/use-in-agent.zh-CN.md) describe how to verify that these instructions are in use.

Checks to run before proposing a change (CI runs the same on Python 3.9 and 3.13):

- `python3 -m unittest discover -s tests -v`, including `tests/test_check_repository.py`.
- Golden files, which exit 1 with a diff on drift: `python3 demo/run_demo.py --check` (English and Chinese reports), `python3 scripts/render_decision_matrix.py --check`, `python3 scripts/render_visuals.py --check`, `readback.py --check` for the Meta and TikTok receipts and `preflight.py --check` for the pre-flight matrix (exact commands in CONTRIBUTING.md). After an intended behaviour change, regenerate with the documented refresh option and read the diff; never hand-edit expected output.
- `python3 scripts/check_repository.py`: required files, workspace paths, tokens and keys, ad account and long numeric IDs, tokens in URLs, referral fragments, and ad-review circumvention or traffic-mixing wording in docs and fixtures. Add new files to its `REQUIRED` list.
- The pre-commit hook (`git config core.hooksPath .githooks`) requires a GitHub noreply author email and runs the checker. Never bypass it to commit real identifiers. Record notable changes in [CHANGELOG.md](CHANGELOG.md).
