# From advertising work to a reusable agent: build order and method evolution

[简体中文](build-from-zero.zh-CN.md) · [Walk through one round](../demo/README.md) · [Operating-loop rules](operating-loop.md) · [Implementation boundaries](architecture.md)

Start by dividing a media buyer's work into steps that can be handed over, inspected and reviewed: connect selected accounts, establish the business and method, prepare trustworthy data and assets, review a batch, verify its results, and bring new observations back to a person. The aim is to reduce repetitive configuration and preparation while retaining human judgement about business direction, test value and strategy.

This guide explains how those steps map to the repository and how methods can evolve. The [demo](../demo/README.md) shows the commands and outputs of one round; this guide does not repeat every example result.

## Separate operational experience, examples and implementation

| Material | What it establishes |
|---|---|
| Problems and experience from advertising work | Context for design, such as missing information, concurrent edits and mismatched readback; turning experience into a rule still requires sources, scope and uncertainty |
| `examples/operating/` and `demo/expected/` | Fictional inputs and outputs produced by actually running the program on those inputs; neither live account records nor evidence that a method improves returns |
| Executable code today | Offline checks, method proposals, test compilation, simulation or operating-loop analysis; no platform connections or ad publishing |
| Intended live-platform design | Requires separately implemented connectors, native field mapping, current permission checks, action authorization and platform readback; documents and file validation cannot supply that evidence |

An output generated by a program run is reproducible evidence of that run. It does not establish that the budgets, account states or after-state differences came from an advertising platform. A checking mechanism is not presented here as a performance strategy proven to improve returns.

## 1. Build the workflow in six steps

### Connect the accounts needed for this task

Identify the platform, native accounts, required operations and connection route, then check read, write and readback capabilities. Official APIs, SDKs, MCP servers and managed connectors are possible routes. Check the selected scope; there is no requirement to connect all three platforms at once.

Today, `onboarding.py` validates supplied simulation snapshots only. Discovering a tool or obtaining `ready_simulation` is not proof of production access. A live adapter must handle native object hierarchies, field units, default states, pagination and error semantics. Replaceable connectors are an architectural aim, not a promise that changing one address puts unchanged code into production. See the [first-run guide](first-run.zh-CN.md) and [integration guide](platform-connectivity.zh-CN.md), both in Chinese.

### Build a sourced business profile

Once connection requirements are clear, establish the product, countries, goals, Web/App surface, monetization, conversion journey, audience, asset direction, budget and measurement definitions. Distinguish user confirmation, observations, unknowns and conflicts. Do not repeatedly ask for known facts.

The host agent can organize answers in conversation, so users do not need to edit JSON. Local code checks structure and workflow dependencies; it neither understands arbitrary language nor verifies source authenticity. Missing information should produce a concrete next step rather than a convenient default. See [business intake](onboarding.md).

### Turn the user's method into reviewable requirements

New users need explanations of variables, constants and observation criteria. Experienced teams need their SOPs, boundaries and exceptions preserved rather than being required to adopt an example strategy. Both paths require an explicit choice of method, separate from batch publishing authorization.

Three representations serve different purposes and are not interchangeable:

| Representation | Current role |
|---|---|
| M1 private text methods and observations | Product-scoped storage, reuse, versions and revocation; adopted text can supply unknown method context, while operational notes remain advisory |
| M2 `MethodSpec` | Two structured test methods: change only the hook within a concept, or explore distinct concepts while fixing at least destination; explicit adoption precedes asset selection constraints |
| Operating-loop `methodology-reference.json` | An example threshold document and action catalog consumed by `operating_rules.py`; maintained and supplied by a person, without the M2 adoption flow |

M2 parses structured answers and explicitly labelled English or Chinese SOP lines only. Unsupported terms and conflicting requirements stay visible; dropping them is not complete understanding of a method. See [method adoption and test planning](method-planning.md) and the [private store guide](private-memory.zh-CN.md).

### Establish measurement before producing findings

Define account and object coverage, dates, time zones, currency, events, attribution windows, the data cutoff and whether late data may still arrive. Assets also need traceable identities. Current test compilation relies on production-manifest or user-confirmed component declarations; it does not watch videos to prove that two assets differ only in their opening.

The operating loop reads externally supplied snapshot JSON and applies the supplied method. It does not collect platform data, and a declared settled observation window is not proof that the data is complete.

- Separate missing values from real zero. Zero clicks can produce CTR=0, but CPC has no usable value when its denominator is zero.
- Separate arithmetic decomposition from causal explanation. The CPM/CTR/CVR log decomposition of CPA needs comparable inputs suitable for calculation. It describes terms in an identity; it does not prove that creative, bids or audiences caused a change. A residual calls for checking rounding and metric definitions rather than assigning a cause.
- Separate observations from method conclusions. Sample, stop-loss and promotion thresholds belong to the supplied method. A triggered rule does not establish applicability to another business or prove that a creative can never work.

### Review the batch and verify before and after a change

A plan should identify objects, evidence, intended field changes, baseline and target values, budget effects, acceptance criteria and stop conditions. Review the concrete batch before executing within the authorized scope. Written acceptance criteria support a handoff, but their presence does not mean every check is implemented.

The operating-loop gate compares baseline, current and target values:

| State | Meaning within the offline comparison | Treatment |
|---|---|---|
| `ready` | Required current values still match the baseline and fields need changing | Include differing fields in the write plan; this is not authorization to write |
| `satisfied` | Target values already hold | Skip redundant writes |
| `conflict` | A current value matches neither baseline nor target | Isolate the row and investigate the change source |
| `unknown` | The object or a required field was not read | Obtain evidence; missing does not mean equal |
| `advisory` | The finding declares no field change | Review separately as advice |

These states concern supplied snapshots. Current `apply` records plans and events; it neither calls a platform nor changes the input snapshot to its targets. `verify` compares targets with a separately supplied after snapshot. The example mismatch is a deliberately constructed test case, not a record of a real API failure.

### Retain the record, then consider changing the method

Distinguish what was proposed, what the user adopted, what was intended to change, what was read back and what remains unresolved. A successful request, matching fields, an ad being able to deliver and improved business results are separate conclusions requiring separate evidence.

The operating-loop JSONL ledger records proposals, skips and reconciliation events. `open` lists proposals still awaiting verification or verified as ineffective. Conflicts, unknowns and advisory items also need `gate.json`, `application.json` and the report; the open count is not a complete task list. There is no background service that revisits platforms, repairs issues, learns performance or promotes observations into general rules.

## 2. Module responsibilities and inputs/outputs

Module boundaries give each kind of change an identifiable place. Frameworks, contracts and methods can all evolve; they need not be described as a permanent design that will never change.

| Module | Main inputs | Outputs and responsibility |
|---|---|---|
| `guidance.py`, `onboarding.py` | Business profile, selected accounts, simulation connection declarations | Connection gaps, collaboration questions, readiness and context snapshots |
| `memory_store.py`, `personalization.py` | Private-store configuration, product scope, explicitly authorized records | Versions and revocation history, matching method context, conflicts and review material |
| `knowledge.py` | Public catalog, business facts, observations | Relevant knowledge, evidence gaps and source-review notices; advice does not expand permissions |
| `methodology.py`, `planning.py` | Structured answers or labelled SOPs, adopted MethodSpec, asset identities | Method candidates and adoption checks, test units, selection and exclusion reasons |
| `task.py`, `adops.py` | Private task profile, method, brief, asset manifest | Versioned methods and batch plans, review files, local simulated objects and recovery checks |
| `operating_rules.py` | Supplied method, ad-set/asset declarations, before and after states | Metric decomposition, rule findings, differing-field plans and target comparisons; a separate entry point loads a method file |
| `operating_loop.py` | Snapshot, method file, before and after snapshots, optional settlement data | Stage JSON, JSONL ledger and report; file and CLI orchestration |
| `demo/` | Fictional inputs in `examples/operating/` | Readable example outputs and drift checks, not platform activity logs |

`contracts/` remains design material that the runtime does not load. Preparation, private methods, knowledge assessment and operating-loop analysis have separate executable entry points. Organizing them into a workflow in documentation does not establish a unified scheduler or native three-platform adapters.

The operating-loop file flow is:

```text
method + data snapshot       -> findings.json
findings + before snapshot  -> gate.json (including a differing-field write plan)
gate                         -> application.json + ledger.jsonl (records, no platform call)
gate + after snapshot       -> reconciliation.json + ledger events
these artifacts + optional settlement data -> report.md
```

The implementation uses the Python standard library to reduce installation steps, Decimal for money operations, and JSON for inspectable stage results. These choices support offline reproduction, but do not eliminate environment requirements, implementation risks or access-control needs. An append-only JSONL convention is not tamper-proof auditing or cross-process idempotency.

## 3. Evolve a method from observation to a new version

The following is a maintenance sequence, not a history of live incidents claimed to have happened:

| Stage | Retain | Current support and remaining human work |
|---|---|---|
| Observation | Date, product, accounts, method version, actual action, native readback/report, anomalies and unknowns | A person or host organizes sources; local code does not collect live evidence |
| Candidate | Hypothesis, scope, counterexamples, proposed changes, acceptance and stop conditions | M1 stores candidates; M2 proposes limited templates; neither proves effectiveness |
| User adoption | Complete selected content, scope and confirmation source | M1 active records express adoption; M2 adopted methods bind candidate content; neither is performance certification or an identity signature |
| New version | Differences, reasons for change and affected tasks | M1 retains versions/revocations; M2 stores revisions; operating-loop method files need manual version maintenance and review |
| Re-evaluation | New comparable observations, deviations from expectations and limitations | Offline checks verify rule and content consistency; business impact still needs independent observation and analysis |

For example, zero conversions alone should not become a claim of ineffective creative. It can motivate a candidate check for sample sufficiency and conversion delay. Its account context, alternative tracking explanations and suitability for another business still need evidence. This example illustrates how to organize experience; it does not claim a particular misclassification occurred here or that the added check has improved live performance.

Keeping supported parameters in a method file can reduce code changes when thresholds change. Boundary cases and resulting outputs still need to be checked. New logic, data semantics or platform actions may require code and tests; adding a JSON field does not implement them. Retain versions and invalidation conditions, and do not change a stable method merely to suggest that the system is continuously learning.

Treat the three change paths separately:

- **M1:** changing or revoking a relevant adopted record affects plans that depend on it. Changes to a candidate or another product do not mean the current method changed.
- **M2:** after adopting a new method, prepare and review a new plan. Do not edit frozen files to reuse an old confirmation.
- **Operating loop:** outputs record method identity, version and content hash for inspection. There is no equivalent M2 adoption receipt, production authorization or automatic method migration. A person reviews the new version before rerunning analysis on fresh snapshots.

## 4. Adapt to different users and businesses

For a newcomer, explain what is being tested, what stays fixed and when to examine data. For an experienced team, establish the existing method's constants, variables, exceptions and unsupported requirements. Both routes preserve sources, conflicts and batch confirmation boundaries; expertise does not expand authority.

Revisit at least these dependencies when adapting the workflow:

| Change | Re-establish |
|---|---|
| Product or revenue model | Conversion events, revenue definitions, quality adjustments, value and payback windows; a fixed-unit-price model is not the default for App or ecommerce |
| Country, platform or ad product | Currency, time zone, events and attribution, object hierarchy, supported fields, media and permissions |
| Team method | Sample criteria, variables, observation windows, budget limits and stop conditions; explicitly list unimplemented requirements |
| Connection provider | Native identity mapping, units, default states, read coverage, write and readback evidence; similar tool names are insufficient |
| User and collaboration preference | Known information, explanation needs, decisions requiring confirmation and the actual scope of allowed automation |

**85% ROAS, 1n1, T-to-2T-to-3T stages and a 3T stop-loss** belong to the example method shown in this repository. They are not universal defaults across the three platforms. The reference formula `T = unit price × quality factor / target ROAS` also depends on that revenue definition. For another model, check the formula and rules before changing parameters.

The current operating snapshot is organized around accounts, ad sets and fixed unit prices. Accepting `meta`, `tiktok` and `google` labels does not establish interchangeable objects or metrics. Live integration must implement and validate native semantics separately; existing file checks are not comprehensive schema compatibility or proof of permissions.

## 5. Validate deliverables, not feature names

Read the [round walkthrough](../demo/README.md), or run from the repository root:

```bash
python3 demo/run_demo.py --steps
python3 demo/run_demo.py --check
```

`--steps` exposes the stages of the same offline loop. `--check` compares selected fresh outputs with `demo/expected/` to detect drift between code and committed examples. It does not verify platform data, every business assertion in prose or advertising performance. Investigate differences before refreshing expected files.

To inspect the standalone analysis entry point:

```bash
python3 operating_loop.py diagnose \
    --snapshot examples/operating/snapshot-primary.json \
    --methodology examples/operating/methodology-reference.json \
    --out runs/build-guide-analysis
```

Use controlled paths and a new output directory for private inputs, and keep real account records out of the public repository. Reuse the explicit steps, inputs, outputs, method sources and verification practices. Each new business or platform capability needs evidence that matches its actual implementation.
