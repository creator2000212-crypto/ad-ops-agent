# 拒审分诊：修正或申诉

[English](disapproval-triage.md) · [实操卡](operations.md) · [文档导航](index.md)

**拒审只能通过修正内容或平台官方复核流程解决。**

本页是广告、创意或媒体素材没能上线时 Agent 遵循的处理流程。它把状态栏里看起来相似的两种情况分开：技术上的上传或处理失败，以及政策拒审。两者处理方式不同，只有前者会再次上传文件。

**范围：**这是宿主工作流程序，[disapproval-triage.json](../contracts/disapproval-triage.json) 是对应的设计契约。公开 Python 代码不调用任何平台，因此不会上传媒体、修改创意、提交复核或轮询审核状态。离线[巡检循环](operating-loop.zh-CN.md)只负责标记：广告组 configured status 为 `ACTIVE` 而 effective status 为 `DISAPPROVED` 时，输出 `AD_STATUS`。

## 分诊一览

| | A. 上传或处理失败 | B. 政策拒审 |
|---|---|---|
| 如何识别 | 解码或格式错误、上传超时、媒体停在 processing、素材引用错误；对象**没有**审核结论 | 平台审核状态为拒审，并给出原因或政策条目 |
| 动作 | 先核对，再按规格重新导出或重新上传**一次**；记录；读回 | 读取原因，然后二选一：修正实质内容后提交修改版，或附证据通过 Request Review 申诉 |
| 完成标准 | 媒体读回 ready，广告引用的是目标素材 | 审核状态读回为通过，且修改或申诉有记录 |
| 停止 | 同一素材第二次技术失败：停止并报告错误 | 同一原因第二次被拒：停止，交人工做政策复核 |

## A. 上传与处理失败（没有拒审）

这类问题出在文件、传输或引用上，内容本身没有被审核判定。

1. **重试前先核对。**超时不等于什么都没创建。先查上传会话、已返回的 ID 和已存在的素材，只补真正缺失的部分。2026 年 9 月 10 日一批 25 条素材上传超时，就是这样处理的。
2. **修正文件或引用，一次。**按规格（封装、分辨率、时长、码率）重新导出，或重新上传一次；引用错误则在所属对象上更正。保留原件，记录派生版本。
3. **记录。**保存平台返回的错误、文件版本、所做动作、返回 ID 和时间。
4. **读回。**确认媒体 ready、各版位预览正常、广告引用的是目标素材。Meta 视频以 `status.video_status = ready` 为准；官方上传器默认不等待编码完成（[VideoUploader，固定 SDK 提交](https://github.com/facebook/facebook-python-business-sdk/blob/5286888addfe3ba3718db65fbf132bd66de3ddfe/facebook_business/video_uploader.py)）。上传成功不等于就绪，就绪也不等于审核通过。

本路线只适用于对象尚无审核结论的情况。对象已被拒审时转到 B：再次上传不是拒审修复。

## B. 政策拒审

1. **读取原因。**记录原生审核状态、给出的原因或政策、所指元素（主张、画面、文案、落地页或其他目的地）以及读取时间。Meta 在广告对象上提供配置状态、有效状态、审核反馈与问题详情（[Ad 模型，固定 SDK 提交](https://github.com/facebook/facebook-python-business-sdk/blob/5286888addfe3ba3718db65fbf132bd66de3ddfe/facebook_business/adobjects/ad.py)）。读不到原因时记录缺口并升级，不猜测。
2. **二选一。**
   - **修正：**修改原因所指的实质内容（主张、画面、文案或落地页），然后提交修改后的版本。提交前向负责人展示修改前后的差异，因为改动主张或落地页就是改动已约定的表达。
   - **申诉：**内容合规、判定看起来有误时，通过平台官方复核渠道（Meta 称为 Request Review）提交，并附证据：广告实际展示内容、落地页，以及支持相关主张的产品资料。
3. **读回。**保存提交或申诉回执，再次读取审核状态与有效状态。审核通过、正在投放、效果表现是三种不同状态。
4. **同一原因第二次被拒即停止。**不再提交。把案例记录（原因、所做修改或所附证据、回执）交给人工做政策复核。计数跟随案例而非对象 ID：新建 creative、广告、换连接器或换账户都不会清零。因不同原因被拒时，在同一记录下另开一轮分诊。

### 禁止

- 重新上传未修改或仅重新编码的素材，以获得新一轮审核。
- 复制被拒广告，或用相同内容新建替代广告，以通过审核。
- 更换广告账户、主页或身份，以通过审核。
- 把新文件、新媒体 ID、新 creative ID 或新广告 ID 报告为修复。只有内容修改或审核结论能解决拒审。

## 每个案例记录什么

| 字段 | 示例（虚构） |
|---|---|
| 案例与对象 | `case-0001`；广告 `ad_demo_01`、creative `cr_demo_01`、视频 `vid_demo_01` |
| 平台返回的原因及读取时间 | “正文含无依据主张”，读取于 2026-01-12T09:40Z |
| 路线 | 修正 |
| 修改或证据 | 正文删除“保证见效”；落地页标题同步调整 |
| 批准记录 | 负责人在批次审阅中批准修改后的文案 |
| 提交回执与时间 | 修改版提交于 2026-01-12T10:05Z |
| 审核读回 | 2026-01-12T14:30Z 通过；广告组 effective status 为 `ACTIVE` |
| 该原因的被拒次数 | 1（第二次即升级为人工政策复核） |

## 追踪内容，而不只是 ID

本地文件摘要、平台媒体引用（`image_hash` 或 `video_id`）、`creative_id`、`ad_id` 与帖子引用（`object_story_id` / `effective_object_story_id`）是不同对象（[AdCreative 模型](https://github.com/facebook/facebook-python-business-sdk/blob/5286888addfe3ba3718db65fbf132bd66de3ddfe/facebook_business/adobjects/adcreative.py)）。分字段保存，使案例历史跟随内容跨对象延续。新 ID 不代表新内容，也不会重置案例。

## 授权

提交修改版和发起 Request Review 都是写操作，与其他变更走同一批次审阅：具体差异 → 负责人批准 → 通过已验证工具执行 → 读回。设计契约、过去的批准或模拟授权都不覆盖这些动作。
