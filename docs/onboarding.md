# 渐进式业务初始化

目标产品在部署后先接入用户选择的系统、读取可用事实，再开展分轮交流。Agent 应掌握足以支撑当前工作的业务背景，后续任务复用这些信息；不要求用户每次重新填写完整简报，也不以完成一份大问卷作为所有工作的门槛。

**本页同时描述宿主的业务访谈方式和 Python 的结构化离线评估器。** 宿主可用已连接工具读取资料并与用户交流，具体能力按当前环境验证；Python 读取 JSON 档案和模拟连接快照，输出摘要、缺口、候选问题与四类 readiness，不做真实连接或模型问答。宿主主路径见[工作流](workflow.zh-CN.md)，代码范围和命令见[能力说明](capability-status.zh-CN.md)。下面的七阶段用于组织访谈，不是必须逐项完成的大问卷。

初始化现在会调用[投放知识库](knowledge-base.zh-CN.md)，根据当前业务与工作流生成 `knowledge-review.json`，并给相关访谈问题附上知识引用和提问理由。补充知识建议不改变现有依赖判定，不会把未知 LTV 等信息升级成所有任务的前置门槛。知识中的其他待核实项目显示在摘要中，实际检查仍需有对应数据和连接能力。

## 首次使用的前置顺序

先完成 MCP/API/SDK 对**本次选定账户**的接入验收，再明确用户如何与 Agent 协作以及当前需求，之后开展业务访谈和工作流。当前离线运行时通过 `connection_gate` 核对读取与 `create_simulated_draft` 写能力的模拟快照：账户、发现状态、scope、时间和 TTL 全部满足才返回 `ready_simulation`。宿主只读报表按所需读取能力验收，不要求发布权限；首次完整写入流程则需要相应写入与读回能力。只装好 MCP、安装 SDK、列出账户或购买服务均不等于验收通过；宿主使用已有工具验证实际能力；若让 Python 自主探测，则需另行实现平台适配器。[首次使用与推荐接入](first-run.zh-CN.md)

在当前 Python 评估器中，连接未就绪时四种 readiness 均不能继续；`next_questions` 不生成业务或用户画像问题，知识建议延后，只输出接入待办及适用的连接器推荐。可以保存已有业务资料，不要求删除或重复输入。独立阅读文档与知识检索不属于广告操作工作流，不受该入口关卡影响。

接入通过后，用 `collaboration.approach` 选择 `guided`（帮助建立方案）或 `bring_own`（沿用已有方法），并明确 `collaboration.current_need`。缺少这两项时先询问协作需求，之后按原工作流收集业务信息。`experience_by_platform` 可分别记录 Meta/TikTok/Google 的 `new/experienced/unknown`，`explanation` 可选择 `detailed/concise`；这些声明不增加账户访问或发布权限。

方法尚未明确时，`guided` 分支用通俗语言收集候选方法所需的信息，`bring_own` 分支请求现有 SOP、结构和观察规则。当前实现的是分流及问题措辞，没有自然语言方法生成或 SOP 解析服务，不会擅自填入已确认方法。生成候选或导入资料后仍需确认并写回带来源的 `facts.methodology`，才能进入依赖该方法的测试规划。

接入偏好放在 `setup_preferences`：`route` 可选 `undecided/pipeboard/existing/self_managed/other_mcp`，`recommendation_dismissed` 用于关闭推荐。它们只控制引导展示；任何选择都不影响真实能力与授权判定。初始化会输出 `setup.json` 和 `setup.md`；CLI 在接入或协作需求尚未就绪时返回 2，并保留这些可读引导文件。

## 三个状态分别回答三个问题

| 状态 | 回答什么 |
|---|---|
| 连接与能力 | 能读取哪些账户、资产和数据，哪些操作有能力依据？ |
| 业务理解 | 当前任务的产品、目标、市场、方法与口径是否已明确？ |
| 任务授权 | 哪个具体计划已经确认，可以在哪些对象与金额范围执行？ |

连接成功不等于理解业务，理解确认不等于批准发布。原型中的 `verified_simulation` 或 `publish=ready` 只说明模拟输入满足规则。

## 自动读取和向人交流如何分工

| 信息 | 优先来源 | 需要人说明的部分 |
|---|---|---|
| 账户、币种、时区、身份与现有配置 | 选择范围内的 API/MCP 只读结果 | 本次使用哪些账户，是否复用现有方法 |
| 产品与目的地 | 用户资料、网站、商店页、落地页 | 产品价值、增长阶段、未来方向与未公开约束 |
| 事件与数据 | 平台、Web 分析、Firebase/MMP/自建系统 | 业务上什么算有效结果，哪些事件只是中间步骤 |
| 收入与结算 | 订单、广告收入、订阅或有效线索汇总 | gross/net 定义、费用、质量门槛和决策窗口 |
| 素材 | 原件、库中元数据、历史引用、可用的 OCR/转写/视觉能力 | 主张真实性、可接受风格、使用依据与加工范围 |
| 投放方法 | 已确认模板与历史配置 | 为什么这样测、固定什么、何时调整，以及适用范围 |

机器可以读取的字段不要反复问人；只读结果不能代表人的未来意图。历史上在某市场消耗，不自动代表下一轮也应投该市场。对来源不可读、调用失败、业务未知与真实零使用不同状态。

## 七个可交错的对话阶段

每轮采用“已知摘要 → 有影响的问题 → 更新理解 → 下一步”。通常一到三个问题，并说明答案会影响什么；允许“不知道”“尚未决定”和“沿用已确认模板”。

| 阶段 | 目标 | 问题示例 |
|---|---|---|
| 1. 项目与接入范围 | 确定产品、目标平台与账户，不自动纳入全部可访问资产 | “发现这些账户与该产品相关，当前先使用哪几个？” |
| 2. 产品与阶段目标 | 明确产品解决的问题和优先业务结果 | “当前更需要验证获客需求，还是降低已定义激活的成本？” |
| 3. 路径、事件与变现 | 理解 Web/App 用户链路及结果含义 | “表单提交之后，哪一步才被业务认可为有效线索？” |
| 4. 市场与人群语境 | 国家、语言、服务范围、使用场景与决策阻力 | “这轮素材要表现哪种使用场景；哪些市场目前无法服务？” |
| 5. 方法论 | 定义问题、变量、固定项、观察和决策原则 | “这轮比较开头还是完整创意方向，哪些内容保持一致？” |
| 6. 素材与配置习惯 | 确定形式、加工、原帖复用、模板与恢复偏好 | “需要保留原帖互动，还是可以接受新的帖子版本？” |
| 7. 理解确认 | 复述关键事实，列出现在能做的任务与剩余依赖 | “这些条件足以整理素材；发布前还差预算和事件映射，理解是否准确？” |

第 6 阶段的恢复偏好只在相关任务出现时询问，不让没有恢复需求的人先填写重传次数或审核流程。问题不是固定脚本，应利用已经读到的证据；没有实际读过演示素材，就不能声称“从你的视频看”。

## 四条业务轴与条件分支

产品至少分别记录：**目的地/路径、变现来源、当前经营目标、本轮测试问题**。混合变现 App 可以本轮只测激活；电商 Web 也可以先看落地页到达质量。任何一条轴都不自动决定其他三条。

| 分支 | 与当前任务相关时需要理解 |
|---|---|
| Web 电商 | 商品、价格、支付、订单 ID、退款、收入 value/currency、净额或毛额 |
| Web 线索 | 表单事件、有效性定义、审核/结算、重复与无效结果、回传延迟 |
| Web/App 订阅 | 试用、首购、续订、取消、退款、费用与观察窗 |
| App 基础 | App ID、OS、商店/分发入口、安装与核心行为、测量系统与覆盖 |
| IAA | 广告收入事件和来源、价值/币种、用户 cohort、收入与留存窗口 |
| IAP | 商品、首购/复购、交易事件、退款/费用、价值口径与成熟度 |
| 混合变现 | 各条收入线、汇总与去重关系、当前目标，不默认收入权重相同 |

事件名字需要业务解释。例如 `purchase` 不自动等于已结算净收入；IAA 的全体活跃用户单日收入也不是新增用户 LTV。有关原生测量字段可参考 [GA4 电商测量](https://developers.google.com/analytics/devguides/collection/ga4/ecommerce) 和 [Firebase 广告收入](https://firebase.google.com/docs/analytics/measure-ad-revenue)；有字段不代表当前数据已正确上报。

LTV、D7 收入、回本周期可以未知。未知不填 0，不强迫使用行业均值；仅阻断依赖这些信息的预测。价值目标需要确认本轮实际使用的价值事件、金额、币种和窗口，不一律要求预测 LTV。

画像用于理解需求与创意表达，优先记录场景、动机、阻力、熟悉度及证据。平台定向是独立配置，不从用户描述推断个人敏感属性并自动编成定向字段。

## 持久业务档案与方法论

目标档案保存内容、类型、状态、来源、观察/确认时间、作用范围与版本。事实、当前配置、偏好、方法、假设和任务决定应分开；状态可以是观察、确认、未知、冲突或过期。置信分数不能代替来源。

作用范围建议为组织→产品→市场/语言→平台/账户→当前任务。一次任务例外不自动改成永久偏好，多个产品共用账户也不意味着它们共用同一个事件含义或素材规则。档案属于项目资料，不默认写入跨项目个人记忆。

一份可复用方法至少包含适用范围、测试问题、测试单元、固定项/变量、配置原则、观察原则、决策方式和授权边界。历史长期使用某预算或结构只是一项观察，经过确认才能成为对应范围的模板。平台无法等价实现时明确列差异。

**当前数据模型更窄：**原型使用 `facts`，每项包含 `value/status/source`，保留 `confirmed/observed/hypothesis/unknown/conflict/stale` 状态。它检查声明形式和有限结构约束，不访问来源、验证业务真实性或解决自然语言冲突；也没有独立偏好继承模型。完整扩展字段见 [onboarding-extensions.json](../contracts/onboarding-extensions.json)，它们尚未全部进入 CLI 输入契约。

## 按工作流就绪，避免全局阻塞

| 目标工作 | 必要信息 | 可以暂时未知 |
|---|---|---|
| 整理业务资料 | 已有资料与允许读取的范围 | 未接的平台、LTV、最终预算 |
| 初筛素材 | 产品事实、市场/语言、表达/规格、候选来源 | 成熟盈利模型 |
| 概念测试草案 | 问题、方法、变量/固定项与预算边界 | 尚待解析的原生配置；草案不能假称可发布 |
| 配置与发布 | 账户/产品能力、目标事件、素材、目的地、预算和确认范围 | 不依赖的其他收入线或长期预测 |
| 整理测试结果 | 测试身份、成本/结果来源、窗口与覆盖 | 收入未知时仍可展示可信的激活等指标 |
| 盈利/回本判断 | 对齐成本、收入、费用、质量与成熟窗口 | 缺关键项则只输出观察值或有条件情景 |

当前运行时固定计算四种 readiness：`discovery`、`material_selection`、`test_planning`、`publish`。四者均先检查读取与必要写入的模拟能力以及协作需求；通过共同入口后，再按各自业务字段评估。`discovery` 可整理合法输入，目前不生成完整七阶段访谈问题。上表描述各项工作的业务信息依赖，不能用于跳过共同接入条件。

缺口应说明影响哪个工作、缺什么、为什么需要、从哪里补以及下一动作。一个平台能力不足只影响相应分支；需要同时起跑的测试单元则按计划整体等待，不能为了推进进度悄悄拆掉实验设计。

## 避免重复问与处理变化

目标行为是：有可靠答案就复用；已问但未知的内容留在缺口中；机器能补的先读取；只有新依赖、重要变化或冲突出现时说明原因再问。

当前程序每轮最多输出三个相关新问题，并在同一输出目录、同一 `profile_id` 下按字段 key 记录已问项。缺口仍存在；不重复输出不代表解决。去重不是语义理解，也不按 `profile_version` 单独区分，档案改版时可能仍沿用旧的已问 key。答案需由输入方更新档案。

| 变化 | 目标产品应重新核对 |
|---|---|
| 产品、价格、承诺、页面 | 素材与文案匹配、链接及依赖计划 |
| 市场、语言、App OS | 本地化、服务范围、事件和配置 |
| 变现、退款、费用、结算 | 价值口径、盈利分析和相关规则 |
| 事件、归因、方法 | 映射、模板、观察窗与可比性 |
| 账户权限、身份、连接版本 | 相应能力与对象引用 |
| 预算、动作、账户范围 | 对应批次授权是否仍然覆盖 |

档案变化不直接修改线上广告，也不反向改写已完成测试。目标是字段依赖级失效；原型采用整个业务内容 hash 的保守失效，提问进度不参与业务 hash。

## 虚构的渐进对话

> Agent：已知资料说明这是一款 Android 编辑 App，当前可用的模拟事件是安装与首次导出。变现和本阶段目标还未确认。先整理已有素材不需要 LTV。
>
> 用户：广告和订阅都有，先降低首次导出的成本；目前没有可靠 LTV。
>
> Agent：记录为混合变现，当前结果是首次导出，LTV 保留未知。这轮希望比较开头、卖点还是整条素材？
>
> 用户：比较开头，正文和 CTA 固定，偏好屏幕演示。
>
> Agent：这套方法用于当前阶段；下次沿用，只核对变化。素材整理已具备条件，发布前还需要本轮账户、预算和原生事件映射。

这个示例展示目标对话体验；当前 CLI 需要显式 JSON 输入，不会自动理解上面的自然语言。
