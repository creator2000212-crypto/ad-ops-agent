# 同一套工作流，两种不同投放方法

[English](method-comparison.md) · [方法与测试计划](method-planning.zh-CN.md) · [项目首页](../README.zh-CN.md)

**以下为虚构的离线示例。** 素材、名称和要求均为演示而设，不是实际建单、真实效果测试，也不表示哪种投法更好。

两项要求从同一批素材出发：视频 `V1` 与 `V2` 的开头不同，但创意方向、正文、CTA 和落地页相同；`V3` 使用另一创意方向，落地页相同。真实任务须先核验素材身份与其他部分是否真的一致。产品资料、观察指标、数据源、窗口和预算上限由使用者提供。

| 使用者要求 | 方案需要保留什么 | 准备批次怎样变化 |
| --- | --- | --- |
| “比较两个视频开头，其他条件保持一致。” | 同一创意方向、正文、CTA、落地页；明确观察指标、数据源与时间窗口 | 把 `V1`、`V2` 的开头作为变化项；若其他部分不一致，先标出缺口再提交测试计划 |
| “探索不同创意方向，保留原计划，另外开测试。” | 原计划及其历史记录不被覆盖；落地页与约定观察口径仍明确 | 新建方案版本，用 `V1`、`V3` 比较创意方向；单独标明执行范围，重新审阅预算上限在原计划与新测试之间怎样分配 |

两种方法共用同一顺序：理解业务 → 准备方案 → 整批确认 → 仅在授权范围内执行 → 逐对象读回 → 按约定窗口复盘。方法和预算由使用者决定。**方案、方法采纳或本地模拟都不等于正式发布授权。**

公开 M2 Python 只支持受约束的 `single_variable` 和 `concept_exploration` 模板，用于**离线**计划与模拟；它要求明确的素材组件身份，不能自行判断视频只有一处差异，也不能证明均匀曝光、随机 A/B 分配或广告效果。已连接的宿主可在工具和任务范围验收后处理更广的用户 SOP；离线模板不是通用投法。[实现与边界 →](method-planning.zh-CN.md)

## 换业务，复用流程

**虚构示例：**使用者从 Web 表单获客转向社交 App 拉新。需求整理、方法确认、整批审阅、结果读回和后续复盘的步骤可以复用。准备新方案前，先替换下列业务输入；本例不代表已经部署接入或验证增长方法。

| 需要重新明确的输入 | Web 线索业务 | 社交 App 业务 |
| --- | --- | --- |
| 目标与结果事件 | 定义清楚的表单提交、有效线索事件 | 选择并定义本次关注的安装、注册或核心互动事件；这些结果不能混用 |
| 质量与收入 | 后端线索有效性、质量及后续收入，如有来源 | 后端用户质量、留存及收入，如有来源；安装本身不能证明这些结果 |
| 归因与数据源 | 平台报表，加已有网站/追踪工具和 CRM 记录；对齐事件口径 | 平台报表，加已有 App 分析、归因服务与后端记录；核验事件映射和覆盖 |
| 观察窗口 | 约定的线索确认、收入成熟窗口 | 约定的激活、留存、收入成熟窗口；不能直接沿用线索窗口 |
| 素材与目的地 | 已核验的权益、CTA 和 Web 表单页 | 已核验的 App 卖点、CTA 及对应商店/深层链接，含系统和地区适配 |
| 执行范围与预算 | 已确认的 Web 产品、账户、权限与预算 | 重新核对 App 身份、平台/账户、读写能力及新范围的拟用预算 |

缺失的事件、来源、窗口和决策阈值先保留未知，取得依据并确认后再使用。不得自动把旧预算、目标成本或用户私有方法复制到新业务。新业务或扩大的范围需要新方案确认，并核对相应权限后才执行获准动作。第一次只读检查可按[首次使用教程](first-check.zh-CN.md)开展；它不授权后续发布。
