# 从零搭一个投放 Agent：架构、模块、数据流与搭建顺序

这份文档按**你实际会做决定的顺序**写。每一步都先讲「遇到了什么问题」，再讲「因此做了什么设计」，
最后讲「这个决定的代价是什么」。读完你应该能自己搭一个同类的东西，而不只是读懂这一个。

配套：[投放快循环规则](../docs/operating-loop.zh-CN.md) · [一轮跑完长什么样](../demo/README.zh-CN.md) · [实现边界](architecture.md)

---

## 第 0 步 · 先画出「它负责什么、不负责什么」

一切设计从这里开始。**如果不先划这条线，后面每一个技术选择都会变成争论。**

投手的一轮循环里有四类劳动：

| 劳动 | 是否交给机器 | 为什么 |
|---|---|---|
| 准备素材、组装配置 | ✅ 交 | 重复、有明确对错，出错成本低 |
| 执行**已批准**的批次 | ✅ 交 | 重复、可回读核对 |
| 解释「实际发生了什么」 | ✅ 交 | 恰恰是最容易算错、也最该留痕的部分 |
| 定方向、判断值不值得、拍板停不停 | ❌ 不交 | 出错成本高，且责任必须落在人身上 |

由此得到三条**硬边界**，它们决定了后面所有的技术选型：

1. **离线优先**：原型阶段不连接任何广告平台。这样「逻辑错」和「权限错」不会混在一起。
2. **人始终在路径上**：产出是给人审阅的动作清单，不是已执行的指令。
3. **不确定就说不确定**：算不出来的一律标「缺证据」，**不用推断填空**。

> 代价：这个原型不能替你改预算。收益：它的每一条判据都能被单独检查和测试。

## 第 1 步 · 分层：把「易变的」和「不变的」分开

一开始最自然（也最错）的做法是写一个脚本直接调 Meta API、算完就改。
问题在于**两个东西的寿命完全不同**：

- 平台接口会变、连接方式会变（官方 API / SDK / MCP / 托管连接器各一套）
- 团队的判据和阈值也会变，但**「怎么判断」这件事的结构不该每次重写**

所以按「变化速度」分五层：

```
┌──────────────────────────────────────────────────────┐
│ 展示层   demo/ · 一页回执                             │  ← 给人看
├──────────────────────────────────────────────────────┤
│ 决策层   operating_rules.py  指标·判据·闸门（纯函数） │  ← 稳定，可单测
├──────────────────────────────────────────────────────┤
│ 编排层   operating_loop.py   快照·台账·回执·CLI       │  ← 稳定，管 IO
├──────────────────────────────────────────────────────┤
│ 契约层   内部能力名 + 输入输出要求                    │  ← 稳定，屏蔽供应商
├──────────────────────────────────────────────────────┤
│ 连接层   官方 API / SDK / MCP / 托管连接器            │  ← 最易变，各家不同
└──────────────────────────────────────────────────────┘
         ▲                                          ▲
         │ 阈值不在这里，在数据里                    │
    方法论文档 methodology.json（每个团队一份）
```

**关键决定：阈值不进代码，进数据。** 目标 ROAS、阶梯、止损线、样本门槛、素材规则、
以及每条动作的自带条件，全部放在一份方法论文档里。换 offer、换单价、换团队 —— 只改那份 JSON。

> 代价：多了一层加载与校验（所以需要 `validate_methodology`）。
> 收益：引擎永远不需要为了「换个数字」而改动，因此也永远不需要重新测试。

## 第 2 步 · 技术选型：每个选择都要能说出「为什么不是别的」

| 选择 | 为什么是它 | 代价 |
|---|---|---|
| **Python 3.9+，仅标准库** | 演示代码必须 `git clone` 完就能跑。零依赖意味着零安装失败、零供应链风险 | 没有 pandas/numpy，统计要从头写（本项目的归因只用 `math.log`，够用） |
| **`Decimal` 而非 `float`** | 预算比较是「相等/不等」判断。`float` 下 `10.00` 可能不等于 `10`，闸门会误判 | 慢一点、写起来啰嗦；但闸门只比较少量字段 |
| **JSON 作为阶段产物** | 每个阶段的输出是**文件**而不是内存对象 —— 可以单独跑、可以 diff、可以提交进仓库当样例、可以断点续跑 | 文件多一点 |
| **JSONL 台账（只追加）** | 状态由事件折叠得出，历史从不被改写；一轮的中间态可复现 | 需要写 `fold()` |
| **无 LLM** | 决策层必须是确定性的：同一输入必须同一输出，否则无法测试、无法复盘 | 自然语言理解交给宿主（对话由外部 Agent 负责，本地程序不做） |
| **离线（零网络）** | 「逻辑错」与「权限错」解耦；也让 demo 能在任何机器上跑 | 真实接入要另写连接器 |

> 一条贯穿始终的纪律：**只有台账的时间戳是「不纯」的**，其余全部确定性。
> 连这一点都用 `--at` 参数钉住了，否则提交进仓库的样例会一次一漂。

## 第 3 步 · 把「一轮」拆到不可再少：数据流从这里自然长出来

**数据流不是设计出来的，是把一轮拆到「每一步只需要上一步的产物」之后自己长出来的。**

先问：一轮里到底发生几件事？

| 阶段 | 手里有什么 | 产出什么 | 由哪层产 |
|---|---|---|---|
| 0 回验 | 上一轮台账 | 还挂着的行 | 编排层 |
| 1 取数 | 平台连接 | `snapshot.json` | 连接层 |
| 2 定性 | snapshot + 方法论 | `findings.json`（含动作） | 决策层 |
| 3 出动作 | findings | （动作对象含在 findings 内） | 决策层 |
| 4 写前闸门 | findings + 写前复拉 | `gate.json`（+ 写计划） | 决策层 |
| 5 执行 | gate.json | `application.json` + `ledger.jsonl` | 连接层（离线＝记录） |
| 6 写后核对 | gate.json + 写后回读 | `reconciliation.json` | 决策层 |
| 7 回执 | 以上全部 | `report.md` | 展示层 |

数据流：

```
 平台/连接器 ──▶ snapshot.json ──┐
                                 ├─▶ findings.json ──┐
 方法论 methodology.json ────────┘                   │
                                                    ▼
 复拉一次 ──▶ writeback.json ──▶ gate.json ──▶ 写计划（只含差异字段）
                                    │                    │
                                    ▼                    ▼
                             （不写的行隔离）      application.json + ledger.jsonl
                                    │                    │
 再拉一次 ──▶ after.json ──────────┴──▶ reconciliation.json ──▶ report.md
                                                          │
                                          ledger.jsonl ───┴──▶ 下一轮的「0 回验」
```

**两个非显然但很关键的后果**：

1. **每个阶段的产物都是文件 ⇒ 可以拿真实产出当样例提交进仓库。**
   这直接解决了「新用户怎么快速看懂」的问题：「不装环境就能看到跑完的样子」。
2. **闸门放在「定性」和「执行」之间，而不是执行之后。**
   因为执行之后再检查只能回滚；放在之前，冲突行根本不用写。

## 第 4 步 · 决策层：一个纯函数模块

`operating_rules.py` —— **无 IO、无状态、无网络**。内部按固定顺序：

```
解析数字 → 推导指标 → 成本归因 → 素材规则 → 逐组定性 → 写前闸门
```

四个实现决定，每一个都对应一类真实事故：

### ① 算不出来就是 `None`，不是 `0`

`CPC = 花费 ÷ 点击`。点击为 0 时 `CPC` **没有值**，不是 0。
但 `CTR = 点击 ÷ 展示`，展示 1000 点击 0 —— 那是**真零**。

两者混同，下游就会把「没有数据」当成「数据是 0」，把缺失读成「表现很差」。
所以：**缺失与零必须分开**，然后在报告里显式标出哪一栏是缺证据。

### ② 判定顺序固定，先过的先赢

不是把指标全算出来一起看，而是过七道关卡：

```
1 账户健康 → 2 硬异常 → 3 指标可算吗 → 4 样本关 → 5 止损线 → 6 利用率 → 7 才谈晋级
```

**顺序本身就是判据。** 一个 CPA 只有 $1.60（远好于目标 $4.71）的组，
如果预算利用率只有 32%，它的结论是「**花不动**，先解决能不能花」，
而不是「表现好，加预算」。顺序保证你先看到利用率。

### ③ 每条动作自带「验收」与「止步」

这是「Agent 在干活」与「Agent 在给建议」的分界线：

```json
{
  "code": "LADDER_PROMOTE",
  "acceptance": "回读 daily_budget = 目标档位金额，且变更流水可查。不一致视为未执行。",
  "stop_condition": "回读发现 bid_strategy 被默认覆盖，或该档未覆盖完整投放日 -> 本轮不晋级。",
  "baseline": {"daily_budget": "10.00"},
  "target":   {"daily_budget": "20.00"}
}
```

- **`acceptance`**：怎么算做完了。没有它，动作永远停在「我说了」。
- **`stop_condition`**：什么情况下**不许做**。这是防止 Agent 越界的唯一办法。
- **`baseline` / `target`**：出方案时读到什么、要改成什么 —— **下一步的闸门完全靠这两个字段工作**。

### ④ 成本归因用对数差，不用「哪个数字大」

`CPA = CPM ÷ (1000 × CTR × CVR)`，取对数后差距可加：

```
log(CPA / CPA基准) = Δlog(CPM) − Δlog(CTR) − Δlog(CVR)
```

三项带符号的贡献各自占总量的比例一起输出。它回答的是「**漏斗哪一段把成本推高了**」，
而不是「哪个数字看起来最大」。残差不为零说明引用值被四舍五入过 —— 这本身是有用信息。

## 第 5 步 · 编排层：IO、台账与回执

`operating_loop.py` 只做四件事，**一行判定逻辑都不写**：

1. 校验快照（缺 `unit_price` 就拒绝 —— 没有 T 就无法判定成本，与其猜不如报错）
2. 调决策层，把结果写成文件
3. 维护只追加台账 + `fold()` 折叠状态
4. 渲染回执 / 提供 CLI

**为什么分成两个模块**：决策层要能被纯单元测试（给定 dict → 断言结论），
不必拉起文件、目录、CLI。所以 49 项契约测试里有 40 项直接调决策层。

---

## 第 6 步 · 用 fixture 把每个分支都逼出来

这是**设计的一部分，不是测试的附赠品**。

只造「正常数据」的 fixture 会让引擎里一半的代码永远不被执行到，于是漏判不会暴露。
所以虚构数据是**按分支倒推造的**：健康的、样本不够的、判死的、超成本的、花不动的、
一个组同时出三类发现的、被拒审的、链接失效的、组名与实际不符的，外加三条账户级信号。

然后还要造**「第二个时刻」的两份快照** —— 这是最容易漏的一步：

| 快照 | 用途 | 里面故意埋了什么 |
|---|---|---|
| `writeback-snapshot.json` | 写前复拉 | 一行**已被人工改过**（现值既非基线也非目标） |
| `after-snapshot.json` | 写后回读 | 一次**写入没有生效**（期望 40，实读 20） |

> 没有这两份，「闸门」和「核对」就只是纸面功能 —— 因为正常数据下它们永远不亮。

## 第 7 步 · 加三道护栏（这才是与「写个脚本算算数」的分界）

到这里引擎已经能算数了。下面三件事才是它真正值钱的地方，**每一件都在 fixture 里有对应的一行**：

| 护栏 | 不做会怎样 | 设计上怎么防 |
|---|---|---|
| **样本关** | 一个零转化组花了 $3 就被判死，而它只是样本不够 | 判死必须**展示门槛与止损线同时越过**；未过门槛只记「未测充分」。贵点击触发早停，但**不下「素材无效」结论** |
| **写后核对** | 接口返回成功就被当成改好了 | 写完再读一次，与 `target` 比对；不一致记「未生效」，**该行继续挂着** |
| **写前闸门** | 出方案期间有人改过 ⇒ 覆盖人工改动，或让整批重做 | 复拉一次，做基线/现值/目标三方比对，五种结果：**只有「可执行」才写，且只发差异字段**；冲突**只隔这一行** |

**闸门的五种结果**（这是整个设计里最值得抄走的一块）：

| 结果 | 含义 | 处置 |
|---|---|---|
| `ready` 可执行 | 现值 = 基线 | 只发差异字段 |
| `satisfied` 已满足 | 现值 = 目标 | **不写**（写了是 significant edit，会重置学习期） |
| `conflict` 冲突隔离 | 现值 ∉ {基线, 目标} | 隔离该行，不覆盖，也不让整批重做 |
| `unknown` 未知 | 没读到，或字段不在快照里 | **先复拉**。缺失 ≠ 相等，绝不放行 |
| `advisory` 仅建议 | 该发现不涉及写入字段 | 不过闸门，单独计数 |

> 最后一种是后来才补的：把「不涉及写入的发现」混进 `unknown`，会让「需要人处理的行数」
> 虚高一倍以上（本项目实测 11 → 2）。

## 第 8 步 · 让评审产物本身也可回读

回执 `report.md` 是给人看的最终产物。但只做到这里还不够 —— 新用户凭什么相信它？
所以再加一层：

1. **把一轮真实运行的产出直接提交进仓库**（`demo/expected/`）⇒ 不装环境就能看；
2. **加漂移校验**（`--check` 重跑并逐字节比对，接进 CI）。

为什么第 2 条必须有：**一份比代码说得更多的样例，比没有样例更糟。**
样例一旦与代码脱节，它就从「证据」变成「误导」。

## 第 9 步 · 框架与策略是两条线：策略是怎么从零长出来的

这是最容易被混淆的一点。**框架**是不变的骨架（分层、契约、闸门、台账）；
**策略**是会随实盘演变的内容（阈值、判据、顺序）。两条线的建立方式完全不同。

### 框架：一次性设计，之后基本不动

分层、阶段划分、五种闸门结果、只追加台账 —— 这些在写第一行代码时就定了，后面只加不改。

### 策略：不是设计出来的，是从每一次失败里长出来的

```
① 先有财务口径：单价 × 有效率 ÷ 目标 ROAS = T
   ⇒ 得到止损线 3T、阶梯 T → 2T → 3T

② 实盘跑一轮 → 发现「零转化的组被误杀」
   ⇒ 加样本关：展示未过门槛的只记录，不判死

③ 实盘跑一轮 → 发现「预算改了其实没生效，却被当成改了」
   ⇒ 加写后核对：回读与 target 比对，不一致就继续挂着

④ 实盘跑一轮 → 发现「出方案期间投手自己改过，方案把它覆盖了」
   ⇒ 加写前闸门：三方比对，冲突只隔离这一行

⑤ 每一轮的新发现 → 沉淀成「判据 + 验收 + 止步」写进方法论文档
```

**这就是为什么阈值必须外置成数据。** 因为策略一定会被实盘反复打脸；
如果阈值写死在代码里，每次打脸都要改代码、重跑测试、重新发布。
外置之后，每次打脸只改一个 JSON 字段。

> 反过来说：**一份从不修改的阈值表，说明它没有在跑实盘。**

### 怎么判断一个新发现该进框架还是进策略

| 问题 | 进框架 | 进策略 |
|---|---|---|
| 换了 offer / 单价，它还成立吗？ | 成立 | 不成立 |
| 它是一个**机制**还是一个**数字**？ | 机制 | 数字 |
| 例 | 「写完必须回读」 | 「止损线 = 3T」 |

## 第 10 步 · 换成你自己的账户

```bash
# 1. 把取数结果整理成同结构的快照
#    照 examples/operating/snapshot-primary.json 的形状写自己的
# 2. 复制方法论改数字（这是你唯一需要改的「策略」文件）
cp examples/operating/methodology-reference.json my-methodology.json
# 3. 跑
python3 operating_loop.py diagnose --snapshot my-snapshot.json \
    --methodology my-methodology.json --out runs/my-round
```

引擎里**没有任何单价、目标 ROAS 或预算倍数被写死**。
动作目录跟着阈值一起走，所以每条动作永远自带它的「验收」与「止步」。

## 一句话总结

> **把一轮拆到每一步只需要上一步的产物，阈值全部抽成数据，
> 然后在「写」之前加一道闸门、在「写」之后加一次回读 ——
> 剩下的就是让每个阶段的产物都能被单独打开看。**
