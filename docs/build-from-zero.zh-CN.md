# 从实际投放工作到可复用 Agent：搭建顺序与方法演进

[English](build-from-zero.md) · [看一轮如何运行](../demo/README.zh-CN.md) · [快循环规则](operating-loop.zh-CN.md) · [实现边界](architecture.md)

搭建这类 Agent，先把投手的工作拆成可以交接、检查和复盘的步骤：接通所选账户，掌握业务与方法，准备可信的数据和素材，生成整批方案，核对操作结果，再把新的观察交给人判断。目标是减少重复配置和整理，让投手保留对业务方向、测试价值和调整策略的判断。

本文说明这些步骤怎样落到仓库模块中，以及方法怎样逐步演进。具体一轮的输入、命令和输出，见 [demo](../demo/README.zh-CN.md)，这里不重复逐条讲解示例结果。

## 先分清经验来源、示例与实现

| 内容 | 应怎样理解 |
|---|---|
| 真实投放工作中的问题与经验 | 为流程设计提供问题背景，例如资料缺失、人工改动、回读不一致；吸收为规则前仍需保留来源、适用范围和不确定性 |
| `examples/operating/` 与 `demo/expected/` | 虚构输入，以及程序使用这些输入实际运行后生成的输出；它们不是实盘账户记录，也不能证明某条方法带来收益 |
| 当前可运行代码 | 离线检查、方法候选、测试编译、模拟执行或快循环分析；不连接平台、不发布广告 |
| 真实平台运行的目标设计 | 需要另外实现连接器、原生字段映射、当前权限验收、操作授权和平台读回；设计文档与文件校验不能替代这些证据 |

“样例来自一次程序运行”只说明输出可以复验。它不表示其中的预算、账户状态或写后差异来自真实广告平台。本文也不把某个检查机制描述为已经被证明能改善收益的投放策略。

## 一、按六步搭建工作流

### 1. 先接通本次要操作的账户

先确定平台、原生账户身份、所需操作和接入路线，再检查读取、写入与读回能力。可以选择官方 API、SDK、MCP 或托管连接器；只检查本次选定范围，无需一次接齐三个平台。

当前 `onboarding.py` 仅校验输入中的模拟连接快照；发现工具或通过 `ready_simulation` 都不是实盘权限证明。真实接入时，需要平台适配器处理对象层级、字段单位、默认状态、分页和错误语义。连接器可以替换是架构目标，不能理解为替换一个地址、其余代码不变就能上线。详见 [首次配置](first-run.zh-CN.md) 与 [接入指南](platform-connectivity.zh-CN.md)。

### 2. 建立有来源的业务档案

账户条件明确后，再掌握产品、国家、目标、Web/App、IAA/IAP/混合等变现方式、转化路径、用户人群、素材方向、预算和测量口径。区分“用户确认”“观察到”“暂时不知道”和“存在冲突”，已知信息不反复询问。

宿主 Agent 可以通过对话整理输入，用户无需自己编辑 JSON。本地代码负责检查结构和工作流依赖，不理解任意自然语言，也不验证来源引用的真实性。对缺项应给出下一步需要补什么，而不是为了让流程继续把它填成默认值。[业务初始化](onboarding.md)

### 3. 把用户方法变成可审阅的要求

新手需要解释候选方案的变化项、固定项与观察口径；资深投手需要保留自己的 SOP、边界和例外，而不是被强制换成示例策略。两者都要明确本轮采用什么，方法采用也不等于批次发布授权。

仓库中有三种不同的承载形式，不能直接互换：

| 形式 | 当前用途 |
|---|---|
| M1 私有文本方法与观察 | 按产品和范围保存、复用、版本化及撤回；已采用文本可以补充未知方法背景，操作观察仅供审阅 |
| M2 `MethodSpec` | 两类结构化测试方法：单一概念下只变 hook，或在至少固定 destination 的条件下探索不同 concept；候选经明确采用后才约束素材选择 |
| 快循环 `methodology-reference.json` | 供 `operating_rules.py` 使用的阈值与动作目录案例；由人维护并传入分析，不经过 M2 的采用流程 |

M2 仅解析结构化回答和明确中英文逐行 SOP 标签。不支持的条款和相互矛盾的要求必须保留，不能删掉后宣称“已完整理解方法”。详情见 [方法确认与测试计划](method-planning.zh-CN.md) 和 [私有方法库](private-memory.zh-CN.md)。

### 4. 先确定数据口径，再生成发现

至少明确本轮账户与对象范围、观察日期、时区、币种、事件定义、归因窗口、数据截止时间，以及数据是否仍可能回补。素材也要有可追溯身份；当前测试编译使用制作清单或用户确认的组件声明，不会观看视频来证明两个素材只差一个开头。

快循环读取外部提供的快照 JSON，再按传入方法计算指标并输出发现。它不负责从平台拉取数据，也不能因为输入带有“已结算”标签就证明数据完整。

- 区分缺失与真零：0 点击可以得到 CTR=0，但 CPC 的分母为 0 时没有可用值。
- 区分数学分解与原因证明：CPA 的 CPM/CTR/CVR 对数差分解需要可比较且适合计算的指标；它说明差异在算式中的组成，不证明素材、竞价或受众造成了变化。残差提示进一步核对舍入与口径，不应直接归为某个原因。
- 区分观察与方法结论：样本阈值、止损或晋级条件属于传入方法。规则触发不证明该方法适用于其他业务，也不证明某条素材永远无效。

### 5. 审阅整批方案，并在操作前后分别核对

方案应说明对象、证据、拟变更字段、原值、目标值、预算影响，以及验收和停止条件。先让用户审阅具体批次，再在已授权范围执行。结构化的验收文字有助于交接，但并不代表程序已经实现了其中每一个检查。

快循环中的写前检查比较“方案基线、写前现值、目标值”，返回五种状态：

| 状态 | 离线判断的含义 | 本轮处理 |
|---|---|---|
| `ready` | 所需现值仍符合基线，存在待变更字段 | 进入差异字段写计划，仍不是实际写入授权 |
| `satisfied` | 目标已满足 | 跳过重复写入 |
| `conflict` | 现值既非基线也非目标 | 隔离该行，核对变更来源 |
| `unknown` | 对象或必要字段没有读到 | 补证据，不把缺失当成相等 |
| `advisory` | 此发现没有声明字段变更 | 单独作为建议审阅 |

这些状态针对提供的快照。当前 `apply` 只记录计划与事件，不调用平台，也不会把输入快照改成目标状态；`verify` 再用另行提供的 after 快照比对目标。示例中的写后不一致是人为构造的测试分支，不是真实接口失败记录。

### 6. 留下记录，再讨论是否改方法

记录应至少区分：提出了什么、用户采用了什么、打算写什么、读到了什么、哪些还需要核对。执行成功、字段一致、广告能投放和经营效果改善是不同结论，需要各自的证据。

快循环的 JSONL 台账保存提案、跳过与核对事件；`open` 列出待核对或核对未生效的提案。冲突、未知和仅建议项还要结合 `gate.json`、`application.json` 与报告查看，不能把 open 数量当成全部待办。当前没有自动回访平台、自动修复、绩效学习或把观察晋升为通用规则的后台服务。

## 二、模块职责与输入输出

模块划分的作用是让不同变化有明确的修改位置。框架、字段契约和方法都会演进；它们不需要被承诺为“设计一次后永远不变”。

| 模块 | 主要输入 | 主要输出与职责 |
|---|---|---|
| `guidance.py`、`onboarding.py` | 业务档案、所选账户、模拟连接声明 | 接入缺口、协作问题、业务 readiness 与背景快照 |
| `memory_store.py`、`personalization.py` | 私有库配置、产品范围、明确授权保存的条目 | 版本与撤回历史、匹配方法背景、冲突和审阅材料 |
| `knowledge.py` | 公共 catalog、业务事实、观察事实 | 适用知识、缺证据与来源待复核提示；建议不扩大权限 |
| `methodology.py`、`planning.py` | 结构化回答/带标签 SOP、已采用 MethodSpec、素材身份 | 方法候选与采用检查、测试单元、素材入选/排除理由 |
| `task.py`、`adops.py` | 任务私有档案、方法、简报、素材清单 | 版本化方法与批次计划、整批审阅、本地模拟对象及恢复核验 |
| `operating_rules.py` | 传入的方法、广告组/素材声明、写前/写后状态 | 指标分解、规则发现、差异字段计划与目标比对；规则函数之外另有方法文件加载入口 |
| `operating_loop.py` | 快照、方法文件、写前/写后快照、可选结算表 | 阶段 JSON、JSONL 台账与报告；负责文件与 CLI 编排 |
| `demo/` | `examples/operating/` 的虚构输入 | 可阅读的演示输出与漂移检查，不是平台运行日志 |

`contracts/` 仍是运行时不加载的设计参考。投放准备、私有方法、知识评估和快循环是已有独立入口；文档把它们组织成完整工作流，不代表已经实现统一调度器或三平台原生适配。

快循环的文件关系可以简化为：

```text
方法 + 数据快照 ──> findings.json
发现 + 写前快照 ──> gate.json（含差异字段写计划）
写前检查结果    ──> application.json + ledger.jsonl（记录计划，不调用平台）
检查结果 + after 快照 ──> reconciliation.json + 台账事件
上述产物 + 可选结算表 ──> report.md
```

当前实现使用 Python 标准库减少安装步骤，以 Decimal 处理金额运算，以 JSON 保存可检查的阶段结果。这样便于离线复验，但不意味着没有环境要求、实现风险或访问控制需求；JSONL 只追加也不等于防篡改审计或跨进程幂等保证。

## 三、方法怎样从观察演进到新版本

下面是一套维护顺序，并非已经发生过的实盘事故史：

| 阶段 | 需要留下什么 | 当前代码能做什么、还需要谁做 |
|---|---|---|
| 观察 | 日期、产品、账户、方法版本、实际动作、原生回读/报告、异常与未知 | 人或宿主整理来源；本地程序不自动采集实盘证据 |
| 候选 | 假设、适用条件、反例、拟改变的条款、验收与停止条件 | M1 可保存候选；M2 可生成限定模板候选；都不证明效果 |
| 用户采用 | 用户选择的完整内容、范围与确认来源 | M1 的 active 表示确认采用；M2 的 adopted 绑定候选内容；二者都不是绩效认证或身份签名 |
| 新版本 | 旧版与新版差异、为什么改变、影响哪些任务 | M1 保留版本/撤回，M2 保存方法修订；快循环方法文件需由维护者手动维护版本并复核差异 |
| 再验证 | 相同可比较条件下的新观察、预期不符的结果和限制 | 现有离线检查能核对规则与内容一致性；方法效果仍需独立的业务观察和分析 |

例如，观察到零转化不能立即归为素材无效；可以提出“先核对样本与回传成熟度”的检查候选。它来自怎样的账户、是否排除了链路问题、是否适合另一个业务，都需要补充证据。这只是如何整理经验的例子，不宣称项目曾发生某次误判，或新增检查已经被实盘证明能提升表现。

把参数放进方法文件，可以减少调整受支持阈值时的代码改动；修改后仍要复验边界与输出。新的判断逻辑、数据语义或平台动作可能需要改代码和测试，不能靠增加一个 JSON 字段自动获得能力。旧规则要保留版本与失效条件，不能为了展示“持续学习”而频繁改动已经稳定的方法。

还要分别处理三条变更路径：

- **M1：**相关已采用条目更新或撤回，会影响依赖它的计划；候选与其他产品的变更不等于当前方法已改变。
- **M2：**采用新方法后重新准备并审阅计划，不能修改冻结文件来沿用旧确认。
- **快循环：**输出记录方法身份、版本与内容 hash，方便比对依据；当前没有与 M2 相同的采用确认、生产授权或自动方法迁移机制。由人复核新版本，再用新快照重新分析。

## 四、迁移到不同用户与业务

面向新手，先解释“正在测什么、哪些保持不变、什么时候看数据”；面向已有成熟方法的团队，先核对原方法的固定项、变动项、例外和当前实现缺口。两种路线都保留相同的来源、冲突与批次确认边界，不根据用户资历扩大权限。

迁移业务时至少重新检查：

| 变化 | 需要重新明确 |
|---|---|
| 产品或收入模式 | 转化事件、收入定义、质量调整、价值与回收窗口；不能把固定单价模型直接当成 App 或电商的默认模型 |
| 国家、平台或广告产品 | 币种、时区、事件与归因、对象层级、支持字段、素材和权限范围 |
| 团队方法 | 样本判断、测试变量、观察期、预算边界和停止条件；超出代码范围的要求明确列出 |
| 连接方案 | 原生身份映射、字段单位、默认状态、读取完整性、写入与读回证据，不能只确认工具名称相似 |
| 用户与协作方式 | 哪些已知、需要多少解释、哪些决定必须由用户确认，以及允许自动执行的具体范围 |

示例中的 **ROAS 85%、1n1、T→2T→3T、3T 止损**属于本仓库展示的一份方法案例，不是三平台通用默认值。参考公式 `T = 单价 × 质量系数 ÷ 目标 ROAS` 也依赖其收入定义。选择另一套模型时，要先确认公式和规则仍适用，再考虑参数，不只是替换数字。

当前快循环快照仍围绕账户、adset 和固定单价组织；接受 `meta`、`tiktok`、`google` 标签不证明三平台对象与指标可以直接互换。生产接入必须分别实现并验收原生语义，现有文件校验不构成全面 schema 兼容性或权限证明。

## 五、按交付物验证，而不是按功能名称验收

先读 [一轮示例](../demo/README.zh-CN.md)，或在仓库根目录运行：

```bash
python3 demo/run_demo.py --steps
python3 demo/run_demo.py --check
```

`--steps` 展示同一离线循环的阶段；`--check` 将新生成的指定样例与 `demo/expected/` 对比，验证样例和代码是否仍一致。它不验证平台数据、文案中每条业务断言或投放效果。样例漂移时先理解差异，不要只刷新预期文件来消除失败。

需要看单独的分析入口，可运行：

```bash
python3 operating_loop.py diagnose \
    --snapshot examples/operating/snapshot-primary.json \
    --methodology examples/operating/methodology-reference.json \
    --out runs/build-guide-analysis
```

替换为私有输入时，使用受控路径和新的输出目录，真实账户记录不提交到公共仓库。可复用内容是明确的工作步骤、输入输出、方法来源和核验方式；每增加一种业务或平台能力，都需要与其实际实现相匹配的验证证据。
