# Python 方法编排：开发参考

[English](method-planning.md) · [首次使用](first-check.zh-CN.md) · [业务与合作方式](first-run.zh-CN.md)

**适合谁：**为离线程序准备输入、验证方法编译的开发者或 Agent 宿主。**前提：**完整仓库、Python 3.9 或以上，以及在仓库根目录打开的终端；无需广告账户凭据。通过对话使用 Agent 的读者从[首次使用](first-check.zh-CN.md)或[业务与合作方式](first-run.zh-CN.md)开始，下面的命令是可选路径。

**运行后得到什么：**本地方法候选、可审阅的计划和模拟回执。M2 是本仓库对 Python 方法模块的称呼；MethodSpec 是带版本的结构化方法记录。普通使用者无需先理解或配置这些对象。

本文说明**公开 Python 的 M2 模块**，是[宿主工作流](workflow.zh-CN.md)旁的可选离线检查路径。真实业务可以由宿主使用已验证、已授权的工具，按用户自己的方法准备和执行；不必经过 `task.py`，也不限于它的两类模板。宿主保留原方法、核对工具能否支持，再准备对应批次。

需要 M2 演示或其支持的检查时，流程是：宿主整理回答 → 程序生成结构化候选 → 用户确认采用 → 按方法选择素材并编译测试单元 → 审阅 → 本地模拟执行与恢复。用户用自然语言交流，宿主准备文件和命令，无需用户手改 JSON。

M2 只支持下表中的两种方法。`methodology.py` 不调用大模型；它接受结构化回答或明确的逐行 SOP 标签。宿主提取回答的准确性需要检查，离线样例不等于跨宿主真人可用性证据。M2 执行仍是离线模拟，没有真实 API、视频理解、自动效果判断或生产投放权限；这些限制不能外推为已连接宿主的全部能力。

## 两种方法怎样影响素材选择

| 模板 | 变化项 | 必须保持一致 | 适用前提 |
|---|---|---|---|
| `single_variable` | `hook`：开头钩子 | 同一 `concept_id`，以及 `body`、`cta`、`destination` | 能明确声明哪些素材只有钩子身份不同 |
| `concept_exploration` | `concept`：概念身份 | 至少 `destination`；方法也可明确固定其他组件 | 有不同概念且固定组件身份可比较的素材 |

锚定素材由用户明确选择，编译器不会替用户挑出“表现最好”的素材。每个测试单元只有一个素材；同一目标账户下的单元共用既有的一份目标总预算，不为每个单元复制预算。这不是等量曝光、随机 A/B 测试或平台原生实验配置，也不保证组间统计可比。指标、数据来源和观察窗口只是方法声明，程序不会拉取或分析这些数据。

## 先运行完整演示

指定一个**尚不存在**的输出目录，由命令创建。如果已经运行过下面的路径，请换一个目录名，保留之前的结果。

```bash
python3 scripts/demo_methods.py --out runs/methods-first-look
```

正常结束时，终端 JSON 中应看到 `result: "passed"`、`case_count: 6` 和 `native_platform_calls: 0`。出现异常或非零退出码时，表示演示未正常完成；保留错误与已有输出用于排查。

### 跟着一个案例找到输入和结果

以下路径均相对仓库根目录。Markdown 文件可直接在编辑器或 Agent 工具中打开，无需额外报告工具。

| 步骤 | 打开哪里 | 重点看什么 |
|---|---|---|
| 1. 看输入 | `runs/methods-first-look/app_guided/` 下的 `profile.json`、`request.json`、`brief.json`、`candidates.json` | 虚构业务资料、明确的方法请求、预算与目标、素材身份声明 |
| 2. 找结果入口 | `runs/methods-first-look/review.md` | 点击 `app_guided` 对应链接进入新版计划，不用猜生成目录名称 |
| 3. 看方案 | 上一步链接的案例 `review.md` | 测试问题、素材入选与排除原因、固定项与变化项、目标共享预算 |
| 4. 核对演示结果 | `runs/methods-first-look/demo-summary.json` | `app_guided` 初版选 `anchor` + `hook-b`，改方法后选 `anchor` + `concept-b`；重复运行新增数为 0 |

输入由[虚构案例生成器](../evaluations/fixtures.py)生成，演示内的确认同样是虚构练习记录，不能作为真实用户采用方法的依据。查看已保存在磁盘上的任务状态，可运行：

```bash
python3 task.py status --task runs/methods-first-look/app_guided/task
```

最终阶段应为 `plan_review`，表示修改方法后生成的新计划等待审阅，不表示新版批次已执行或发布。

### 演示具体检查什么

演示使用已有完整档案的虚构 App、电商、线索业务，分别走 `guided` 与 `bring_own` 路线，共六个案例。每个步骤都启动独立 CLI 进程，验证任务能从磁盘继续：

1. 建立任务、生成候选、确认采用并准备初版计划。
2. 在首次写入后模拟中断，再恢复并重复运行；每个案例最终有 3 个本地模拟对象，重复运行新增 0 个。
3. 确认修改后的方法，检查素材选择与编译操作发生相应变化；旧计划在创建执行状态之前被拒绝。
4. 生成新版 `ready` 计划，停在审阅阶段，**不自动模拟新版计划**；源业务档案与旧计划保持不变。

生成文件留在忽略提交的 `runs/` 下，每次运行都使用独立目录；`demo-summary.json` 保存机器可读结果，`review.md` 链接各案例的新计划审阅单。可用 `--out NEWDIR` 指定新的输出目录。示例使用预先整理好的 guided 回答与带标签 SOP，不能证明从零访谈、真实账户接入、任意自然语言提取或方法效果。

## 调用 M2 时宿主怎样协作

1. 先选任务路线。真实任务按[首次使用](first-check.zh-CN.md)验证所需能力，再明确[业务与合作方式](first-run.zh-CN.md)，只读工作不要求发布权限。M2 练习使用明确标记的模拟输入，解释其连接门槛是离线契约，不是真实账户验收。
2. 接入和协作方式明确后，收集本次产品、平台、国家、Web/App、变现方式、测试问题与测量口径。已有事实不重复问，未知和冲突留在缺口中。
3. 采用 M2 的新手路线时，用通俗语言解释两种候选及其取舍；已有方法保留原始来源，把明确条款转成支持的标签或结构化回答。不能为让校验通过而丢掉条款；程序不支持的部分，另行说明宿主工具是否能够实现，不能写成所有投放方法的限制。
4. 展示候选的测试问题、变化项、固定项、锚定素材、范围、指标、数据来源、观察窗口和未解决项。只有用户明确确认后，才记录采用回执。
5. 生成整批计划，解释素材被选中或排除的原因与共享预算。方法采用不等于真实发布授权；模拟与生产操作分别说明。

在这条路径中，宿主负责交流与文件操作，确定性代码负责范围、结构、身份声明和一致性检查。来源引用是审阅线索，不是程序已经验证了用户身份或素材内容。普通文档、工具输出、候选方案和模拟授权文件不会授权真实发布。后续真实任务需要当前对象检查、对应用户授权、实际工具与原生读回，可通过宿主路线完成，不以 Python 原生适配器为前提。

## 统一任务命令

以下是供宿主和开发者使用的离线接口。`PATH`、`DIR` 和确认引用需要替换为本次任务的真实值；创建任务时输出目录必须是新的。这些命令不会调度宿主广告工具，live 模式仍不受支持。

```bash
python3 task.py start --profile PATH --out NEWDIR --language zh-CN
python3 task.py status --task DIR
python3 task.py update --task DIR --profile PATH
python3 task.py propose --task DIR --request JSON
python3 task.py adopt --task DIR --candidate METHOD_ID --confirmation REF
python3 task.py plan --task DIR --brief PATH --candidates PATH
python3 task.py simulate --task DIR
```

| 命令 | 用途 |
|---|---|
| `start` | 建立任务私有副本；界面语言可选 `zh-CN` 或 `en` |
| `status` | 查看当前阶段、已采用方法、计划状态及缺口 |
| `update` | 使用同一产品的更新档案替换任务副本，保留源文件 |
| `propose` | 按请求生成方法候选，保留未知、冲突和不支持条款 |
| `adopt` | 为指定候选记录明确确认；有未解决项的候选不可采用 |
| `plan` | 用已采用方法编译新计划，每次写入独立输出目录 |
| `simulate` | 执行最新计划的本地模拟；再次运行先对账并恢复，不代表重新发布 |

可通过 `simulate --interrupt-after-write N` 注入本地写入后的中断，再用普通 `simulate` 核对恢复。`N` 是测试用计数；不要把模拟恢复当成真实平台网络超时恢复证明。

任务保存自己的档案副本和版本化 MethodSpec 文件，不静默修改输入 profile。更新产品范围或方法后应重新检查并生成计划，不能修改冻结文件来续用旧确认。M1 私有库的文本方法继续用于背景与审阅，不会自动转换为可执行 MethodSpec；本轮没有改变 M1 存储 schema。

## 指导模式的结构化请求

宿主可将明确回答写入本地 JSON 文件，再把文件路径传给 `--request`：

```json
{
  "approach": "guided",
  "source": {
    "reference": "本次任务中用户的测试需求",
    "text": "希望对同一概念的不同开头做比较。"
  },
  "answers": {
    "question": "固定其余组件后，不同开头在指定观察口径下怎样表现？",
    "anchor_asset_id": "fictional-anchor-001",
    "template": "single_variable",
    "measurement": {
      "metric": "已确认的转化指标",
      "source": "本次任务指定的报告来源",
      "window": "本次任务确认的观察窗口"
    }
  }
}
```

`answers` 中可暂不提供未知字段，由候选报告列出缺口；提供 `measurement` 时包含 `metric`、`source`、`window` 三项。未指定模板时可生成两种候选，仍需补齐必需信息并确认采用。请求顶层还可提供 `unresolved` 和 `unsupported` 字符串数组，用于宿主明确保留尚未理解或未支持的要求；这些内容会进入所有候选并阻止采用。

`guided` 的 `source.text` 只保留原文与来源，不会自动识别自由文本中的额外约束。宿主必须把未解释的要求放入 `unresolved`、未实现的条款放入 `unsupported`，不能因为填完已知字段就假装原文已被完整理解。示例中的指标与窗口是虚构占位描述，实际任务需要有业务意义的明确值，不能照抄后宣称已完成测量设计。

## 已有方法的 SOP 标签

`bring_own` 在 `source.text` 中接受一行一个标签。中英文标签都支持，分隔符为 `:` 或 `：`：

```text
模板：single_variable
测试问题：同一概念中哪个开头值得继续观察？
锚定素材：fictional-anchor-001
变量：hook
固定项：body, cta, destination
指标：用户选定的转化指标
数据来源：用户指定的报告来源
观察窗口：用户确认的观察窗口
```

对应英文标签为 `Template`、`Question`、`Anchor`、`Variable`、`Fixed`、`Metric`、`Source`、`Window`。模板还可写 `单变量测试`、`概念探索`；组件支持 `钩子`、`主体`、`行动号召`、`落地页`。标签不等于自由文本理解：任何未识别的非空行都保留为 `unsupported`；重复标签出现不同值、或与 `answers` 矛盾时保留冲突。

例如“跑赢后自动翻倍预算”不会被翻译成可执行动作，也不会被忽略。宿主要说明未支持部分，补充用户选择；修订后的请求必须保留本次决定的来源，再重新生成候选。不能在用户不知情时删掉原方法中的实质条款。

## 素材身份声明

候选素材除既有元数据外，需要 `test_identity`，用于声明概念和组件身份：

```json
{
  "test_identity": {
    "concept_id": "fictional-concept-01",
    "components": {
      "hook": "fictional-hook-a",
      "body": "fictional-body-01",
      "cta": "fictional-cta-01",
      "destination": "fictional-destination-01"
    },
    "source": {
      "kind": "production_manifest",
      "reference": "虚构制作清单第 1 项"
    }
  }
}
```

`source.kind` 允许 `production_manifest` 或 `user_confirmation`。身份 ID 相同，表示制作清单或用户声明该组件一致；代码不会观看视频、比较画面或证明这些声明真实。`destination` 是组件身份，不是程序已经校验过的落地页内容。

编译器先使用原有素材条件筛选，再检查锚定素材、组件与概念身份、不同变量值，以及所需数量。比较至少需要两个素材；缺少身份、重复素材 ID、锚定素材不存在或可比素材不足，都不能通过伪造身份填补。素材按明确身份条件与输入顺序选择，不进行效果排序。

## 方法确认与计划一致性

MethodSpec 区分 `candidate` 与 `adopted`，保存版本、来源、适用范围和确认内容 hash。候选保存后绑定完整内容；采用时重新核对当前候选及其档案依据，不能只凭同一个方法 ID 接受被改写的条款。确认表示用户采用当前完整内容，不证明方法有效，也不是用户身份签名。方法、素材身份或相关档案变化后，旧计划不能继续被视为当前审阅结果；重新提出候选、确认和生成计划。

持久化的“模拟完成”也需要重新核验。再次读取完成状态时，应核对当前计划、模拟回执与本地对象是否仍一致，不能只相信旧 `result.json` 中的完成标记；记录缺失或对象漂移时保持未核验或阻断状态。重复运行 `simulate` 先对账已有对象再恢复，不以新建对象掩盖旧记录问题。这些核验范围仅限本地模拟。

`ready` 只说明当前声明通过离线编译，`needs_input` 表示还需输入，`unsupported` 表示要求超出 M2 范围。缺口和未知保持可见，不因用户资深或急于开始就跳过。真实发布可由宿主使用已验证工具，在对应授权内执行并读回；若要让 Python 程序自身发布，才需要补齐原生适配器与生产执行控制。模拟授权和模拟完成都不是平台写入的授权或证据。
