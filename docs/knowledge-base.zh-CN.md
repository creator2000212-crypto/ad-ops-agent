# 投放知识库与 Agent 的工作方式

知识库把投放经验整理成 Agent 可以检索、判断适用条件、列出证据缺口并用于方案审阅的条目。它服务 Meta、TikTok、Google Ads 的通用工作流，也保留平台、Web/App、变现方式和当前任务阶段的差异。

当前已接入离线运行时：`knowledge.py` 读取 `knowledge/catalog.json`，业务初始化输出知识建议，计划生成时把相关知识与批次审阅绑定。它使用确定性检索和结构化条件判断，不调用大模型、不拉取广告数据，也不会根据一条经验自行修改预算、改变受众或发布广告。

M1 增加按需启用的[产品私有方法库](private-memory.zh-CN.md)：本地 SQLite 保存产品方法与操作观察，`personalization.py` 解析匹配条目，使初始化、计划和独立知识评估都能结合公共知识与私有经验。已采用方法用于补充未知的方法论，已有不同方法时保留冲突；操作观察始终只提供建议。

## 宿主怎样吸收实际经验

[真实案例](case-studies.zh-CN.md)解释检查要求从哪里来，不能当作所有平台通用规则。宿主按[工作流](workflow.zh-CN.md)将相关条目用于资料补缺、选材理由、方案审阅和读回清单；工具获取本次证据，用户确认自己的方法。发现旧报告状态与读取不一致时，先修正当前结论，再形成带范围的候选经验。私有对话、固定业务阈值和客户素材不进入公共目录。

当前 `knowledge.py` 的结构化检索仍是离线组件；新增案例文档没有自动转换成代码规则，也不会自行调用平台或写入私有记忆。用户明确要求保存的方法，按私有库的范围与版本规则处理。

## 从“有经验文档”到“工作时用得上”

现有的 [16 张实操卡](operations.md) 和 [Meta 素材恢复说明](meta-creative-recovery.md) 仍适合人阅读。运行时知识库把可复用部分拆成带来源、范围、前提、证据和下一步的条目，使 Agent 能回答：

- 当前阶段应该知道什么？哪些缺项会影响后面的判断？
- 这条知识是否适合当前平台、业务和变现方式？
- 哪些输入是已知事实，哪些只是未知、冲突或假设？
- 建议的依据是什么，需要先补充哪份数据或原生状态？
- 怎样验证操作结果，什么情况下应停止沿用这条经验？

知识库提供判断依据与检查建议。预算、测试目标、观察周期及团队方法论仍来自业务档案或已确认方案；它不会内置一套适用于所有业务的固定 CPA、ROAS、花费倍数或扩量比例。

## 首批知识覆盖

当前版本含 40 条知识、19 项来源：15 项官方文档或官方 SDK 来源，以及 4 项本项目的方法与工程说明。完整结构化内容见 [catalog.json](../knowledge/catalog.json)。

| 领域 | 条目 | 重点 |
|---|---|---|
| 业务理解与收入 | `KB-CONTEXT-01..03`、`KB-APP-01`、`KB-WEB-01`、`KB-IAA-01`、`KB-IAP-01`、`KB-HYBRID-01`、`KB-SUB-01`、`KB-ECOM-01`、`KB-LEAD-01`、`KB-VALUE-01` | 产品、人群、路径、方法、收入事件与价值窗口 |
| 素材与实验 | `KB-CREATIVE-01..02`、`KB-TEST-01..02` | 概念与文件区分、承诺一致性、实验变量、样本与观察窗口 |
| Meta / FB | `KB-META-01..08` | 视频就绪、对象身份、原帖互动、预览与增强、有效状态、预算归属、复制和拒审诊断 |
| TikTok / TK | `KB-TK-01..04` | Spark 身份授权、广告产品规格、安全区、Pixel 与 Events API 去重 |
| Google Ads / GG | `KB-GG-01..04` | RSA 组合、追踪层级与并行路径、转化延迟、系列转化目标 |
| 测量与排障 | `KB-DATA-01..03`、`KB-DIAG-01..03` | 覆盖、成本缺失、跨源口径、漏斗、素材衰退与掉量 |
| 执行与经验维护 | `KB-EXEC-01`、`KB-LEARN-01` | 不确定写入、并发修改、案例与反例、审核后沉淀 |

这里的数量代表知识覆盖，不代表 40 项平台操作已实现。来源中的复核周期是项目维护安排，不是平台公布的有效期。

## 先运行一次

在仓库根目录执行。只需 Python 标准库，无需账户凭据。

```bash
python3 knowledge.py search --query '归因' --stage measurement --platform meta
python3 knowledge.py search --query '素材' --stage creative --platform tiktok
python3 knowledge.py search --query '转化' --stage diagnosis --platform google
```

`search` 用来浏览知识。`--stage`、`--platform`、`--surface`、`--monetization` 是可选范围，`--stage` 默认 `diagnosis`；可用阶段为 `discovery`、`planning`、`creative`、`launch`、`measurement`、`diagnosis`。`--limit N` 默认 12，允许 1–200。检索按关键字与显式条件匹配，不会理解查询句子的语义。省略业务档案时，程序会保留范围或证据未知的状态，检索命中不等于已经证明适用于某个账户。

用虚构业务档案和虚构观察事实生成审阅报告：

```bash
python3 knowledge.py assess --profile examples/onboarding-learning.json --observations examples/knowledge-observations.json --stage diagnosis --out runs/knowledge-review
```

输出目录包含：

| 输出 | 用途 |
|---|---|
| `report.json` | 供程序继续处理的结构化评估结果，保留知识身份、状态、证据与来源 |
| `review.md` | 供投放人员阅读的建议、缺口与后续核验事项 |

这些命令会分析输入文件的结构化事实，不会连接示例中的账户。模拟连接快照也不能证明真实 API 权限有效。

## Agent 在三个位置使用知识

### 1. 初始化：先把该知道的事情问清楚

`onboarding.py` 原有的业务就绪检查继续负责产品、国家、平台、目标、转化路径、受众、素材方向、方法论和测量条件。知识库为结果增加 `knowledge_review`，另存 `knowledge-review.json`，并为匹配到知识的后续问题附上相关依据，使用户知道为什么现在需要补充这项信息。

访谈依据业务分支展开。例如 App 项目需要说明系统、商店与测量方式；IAA、IAP、混合变现需要分别说明收入事件和口径。未知 LTV 应保留未知，不应为了开始素材测试而编造一个值。知识建议不能替代已有就绪依赖，也不会让没有写入权限的账户变得可发布。

当前交互仍是结构化 JSON 输入与规则生成的问题，不是自然语言聊天机器人。未来接入 LLM 时，模型可帮助解释和收集信息，但已确认事实、来源及状态仍应写回同一套业务档案。

### 2. 计划：把经验变成可审阅的检查项

`adops.py` 在生成批次计划时使用 `planning`、`creative`、`launch` 阶段知识，帮助审阅测试设计、素材准备和发布前条件。相关报告随计划输出，不会暗中改变用户的预算或执行范围。

公共知识库内容的 hash 随计划冻结。公共库发生变动后，旧计划需要重新生成、重新审阅并重新生成模拟授权。启用私有方法库时，另冻结本次产品与范围匹配的 `active` 条目；这些条目更新或撤回也要求重新准备。条目的 `stages` 控制知识审阅中的呈现，不再缩小该私有依赖快照。候选条目、其他产品或不匹配范围的私有改动不影响该依赖快照。现有计划 hash、业务档案漂移检查和模拟权限检查继续有效。

来源新鲜度按报告中的 `as_of` 日期计算；跨日自然过期不会自动改变已冻结报告或撤销模拟授权。长时间搁置后应重新生成评估。真实发布接入还需要操作当时的平台能力与来源复核。

这里的素材检查仍基于提供的元数据和观察事实。当前代码没有打开图片、观看视频、审核文案或读取真实版位预览。

### 3. 诊断：把观察、解释和下一步分开

`knowledge.py assess` 接受业务档案与另外提供的观察事实，按条件找到相关知识。报告可以组织“已提供的证据 → 可能原因 → 还需确认的证据 → 下一步检查”，帮助投放人员分析。

例如看到“转化减少”，先确认是否有相同账户范围、日期、时区、归因口径和足够成熟的数据，再判断素材或人群是否需要调整。看到“广告未投放”，先检查对象层级、有效状态和可用素材，而不把预算增加当作默认答案。

这不是自动统计分析或因果证明。程序不会自动计算显著性、预测素材表现或证明某次操作带来收益。只有补齐相应事实后，知识建议才可能由待补充状态变为适用；最终决策仍需要结合业务目标与完整数据。

## 怎样理解结果状态

| 状态 | 含义 | 接下来怎样做 |
|---|---|---|
| `applicable` | 当前提供的背景和证据满足该条目的适用条件 | 阅读建议和核验步骤，按任务授权决定后续动作 |
| `needs_context` | 缺少判断适用范围需要的业务背景 | 补充平台、Web/App、变现等相关背景，不直接套用 |
| `needs_evidence` | 需要的观察事实不足、未知、冲突或未确认 | 获取所需记录或读回结果，保留来源后再评估 |
| `needs_source_review` | 来源超过复核周期，或复核日期晚于本次评估日期 | 重新查看原始来源，核对日期、当前版本、广告产品和账户支持 |

所有结果均为 `advisory_only`。`applicable` 只说明知识条件得到满足，不表示建议已获操作授权、已经执行或一定有效。某条知识没有被返回，也不代表对应问题已排除。

显式范围不匹配的知识应被排除。范围未知时保持待补充状态，不能把“不知道”处理成“符合”。例如 TikTok Spark 的条件不能直接用于 Meta 广告，App 收入测量也不能自动用于 Web 项目。

## 提供可用事实

业务背景保存在已有 profile 中。新观察使用独立文件，顶层是 `schema_version` 和 `facts`；每个事实保留 `value`、`status` 与 `source`。仓库的 [虚构观察示例](../examples/knowledge-observations.json) 提供可直接运行的输入。

```json
{
  "schema_version": 1,
  "facts": {
    "your_observation_key": {
      "value": "记录中实际观察到的值",
      "status": "observed",
      "source": "能追溯的文件、报告或原生对象读回记录"
    }
  }
}
```

上面的键只是格式示例。要触发具体知识，请使用该条目要求的事实键，不要把自由描述误当成已被解析的广告数据。允许的状态为 `confirmed`、`observed`、`hypothesis`、`unknown`、`conflict`、`stale`；只有带来源且有值的 `confirmed` 或 `observed` 可以作为条件证据。`false` 和 `0` 可以是实际观察值，不能擅自替换成未知。对暂时无法确认的情况保留相应状态；未知、假设、冲突不能当成满足条件的证据。

一次评估使用一致的产品、账户范围、时间窗和统计口径。不同业务或日期的观察应分开评估，当前程序不会自动发现混在同一份文件中的口径差异。已确认的触发条件与条目不匹配时，条目会被排除；触发条件未知时，只提示缺少证据。

独立知识评估检查事实的状态、来源和非空值，不会核实引用的真实性，也不完整校验每个业务字段的语义类型。完整业务输入继续先经过 `onboarding.py`；不能用 `applicable` 替代业务档案校验、真实测量或原生状态读回。

profile 与 observations 出现同名事实键时，程序拒绝覆盖。先核对冲突并更新事实来源，再重新评估，避免观察文件悄悄改写产品或业务目标。

文件中不应包含访问令牌、账户密码或支付信息。私有报告可保存在本地、受控路径；公开示例继续使用虚构账户、素材和数值。

## 知识分层与来源管理

知识条目不能因为写进 JSON 就成为平台规则。运行时区分四类内容：

| 内容 | 如何表述 | 怎样使用 |
|---|---|---|
| `platform_fact`：官方平台事实 | 来源支持的字段、对象关系或产品行为，限定平台和版本范围 | 核对当前来源、账户能力及广告产品后使用 |
| `operational_principle`：通用操作原则 | 工程检查、证据保存、数据口径或诊断顺序 | 用作操作检查，不伪装成平台强制要求 |
| `strategy_template`：方法模板 | 测试假设、变量、观察条件和成功标准的组织方式 | 结合业务选择参数，不写死预算或绩效门槛 |
| `diagnostic_hypothesis`：诊断假设 | 特定条件下可能的问题原因与排查路径 | 结合实践观察补充证据，不从一次成功推出通则 |

条目保留来源，以及 `checked_on`、`review_after_days` 等复核信息。来源链接存在不等于其中全部内容支持该条建议；复核时需要检查具体事实与引用是否一致。官方事实超过复核周期后，应降低其可用状态并提示复核，不能自动把日期更新为今天。

平台审核、API 能力、规格与权限会变化。当前公开知识不承诺覆盖全部国家、广告产品、账户版本或原生设置。一般方法与案例也需要持续检验，但不应冒充官方要求。

## 把团队经验沉淀成知识

建议用下面的顺序吸收新的投放经验：

1. **保留原始观察。** 写明平台、广告产品、业务模式、对象层级、时间范围、输入事实和异常现象。
2. **区分动作与结果。** 分别记录尝试了什么、请求是否被接受、读回是否一致，以及观察了多久。提交成功不等于投放成功。
3. **写清假设与反例。** 说明认为可能相关的因素、尚未排除的原因、风险、失败条件及必要的停止条件。
4. **限定可复用范围。** 去除私人标识，保留真正影响结果的条件；不能把某个 Offer、账户或素材的表现写成三平台统一策略。
5. **人工复核后入库。** 对平台事实补充当前官方证据；对经验标明来源类型与不确定性；增加适用、缺项、不匹配等测试。
6. **在新任务中再次验证。** 收集结果作为下一轮维护依据，不能因为建议被执行就把案例自动提升为通用规则。

当前可通过 `memory_store.py` 将用户明确授权保存的方法、纠正或观察写入产品私有库，并保留版本与历史。任务观察可先保存为 `candidate`；只有用户明确确认采用，且来源为 `user_confirmation` / `user_statement`，才可写为 `active`。这表示采用意愿，不表示效果已验证。自然语言学习、自动反馈提取和自动经验晋升仍未实现；公共知识文件的修改继续需要人工审阅，任何条目写入都不触发广告账户操作。

例如“更换媒体引用后审核结果变化”只能记录为一个带条件的观察。需要区分文件 hash、平台媒体 ID、creative ID、ad ID、post ID，以及技术故障、审核误判和内容问题；不能据此生成“改 hash 就能恢复投放”的自动规则。相关处理边界见 [Meta 素材恢复](meta-creative-recovery.md)。

## 公共知识与私有知识

默认使用仓库的 `knowledge/catalog.json`。需要跨任务复用产品方法与团队观察时，在业务档案中显式配置 `private_memory`，使用[私有方法库](private-memory.zh-CN.md)；省略或关闭配置时维持公共知识流程。私有库按 workspace 与产品隔离，匹配的已采用方法只在 `facts.methodology` 缺失或 `unknown` 时补充本次评估。不同有效方法同时出现时保持冲突，不静默覆盖源档案。`operational_note` 只供审阅，不会更改预算和执行权限。

快速体验完整路径：

```bash
python3 scripts/demo_private_memory.py
```

单独需要替换本次公共 catalog 文件时，仍可使用 `--catalog`：

```bash
python3 knowledge.py assess --profile examples/onboarding-learning.json --observations examples/knowledge-observations.json --stage diagnosis --catalog /absolute/path/team-knowledge.json --out runs/team-knowledge-review
```

`--catalog` 选择本次独立评估的 catalog 文件，不会将其导入私有数据库，也不会上传文件。初始化与计划仍使用项目默认公共 catalog，另按档案配置读取私有库；独立评估临时选择的 catalog 不会自动替换其他工作流的公共来源。私有文件的脱敏、文件访问权限与备份由维护者负责；本地产品隔离不是多租户认证。

新增公共条目前请阅读 [贡献说明](../CONTRIBUTING.md)。`contracts/experience-catalog.json` 等设计文件仍保持 `design_only`，运行时不会自动执行其中的候选能力；真正加载的知识在 `knowledge/` 下。不要靠修改设计状态标记宣称功能已经实现。

## 验证改动

```bash
python3 -m unittest discover -s tests -v
python3 scripts/demo.py
python3 scripts/check_repository.py
```

知识相关验证应关注错误套用的后果：不同平台和变现方式不会混用；未知、冲突和假设不会变成证据；过期来源会被提示；同名事实不会被静默覆盖；知识改版使旧计划失效；任何建议都不会获得额外写入权限。只有实际运行通过的检查才能写成已验证结果。
