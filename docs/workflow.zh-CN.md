# 把实际投放工作交给 Agent

[English](workflow.md) · [真实工作案例](case-studies.zh-CN.md) · [能力范围](capability-status.zh-CN.md)

本页是宿主 Agent 的工作说明：在 WorkBuddy、Codex 等环境中，如何使用已经接好的工具，把一项投放任务从需求做到结果交接。它来自历史工作记录的提炼；接入新宿主后，仍要检查该宿主实际有哪些工具和权限。

这条路线可以调用宿主已有的 MCP、API、SDK 或用户允许的后台操作。仓库的 Python 程序是另一条离线验证路线，不承担这些真实调用，也不是使用宿主工具的前置条件。

## 从用户当前要做的事开始

| 用户可能这样说 | 先弄清什么 | 交付什么 |
|---|---|---|
| “用这批视频做下一轮测试” | 产品与落地页、账户、事件、测试问题、素材能否匹配 | 选材理由、排除项、整批配置与预算 |
| “按确认方案搭建或调整这批广告” | 批次版本、对象与动作、预算、依赖、当前状态和用户授权 | 逐项操作记录、配置读回、部分失败与未完成项 |
| “检查这些账户，哪些需要调整” | 时间范围、账户覆盖、当前方法、上一轮未完成项 | 数据与依据、调整建议、缺数与后续待办 |
| “把这条计划迁到另一个账户” | 源结构、目标权限、身份/事件/媒体能否复用、重叠预算 | 新旧对象对应、迁移差异、获准操作与核对结果 |
| “这个广告不花钱 / 被拒 / 配置不对” | 实际状态、父级对象、审核或报错、最近变更 | 问题定位、证据、恢复选项与结果 |
| “按 Offer 给我日报” | 日期/时区、渠道与账户、费用/转化/收入来源、归属规则 | 清晰报告、覆盖说明、可追溯明细 |

先选择当前任务，再补所需信息。用户只是要报表时，不必让他重新回答素材测试问题。

## 1. 确认这次能操作哪些东西

记录本次平台、账户和任务所需工具。用授权范围内的读取验证身份、账户范围、币种/时区，以及所需对象和字段是否可读。需要写入时，再核实对应创建/修改能力和结果读取能力；不要为了测试权限新建广告。

- **首次搭建完整投放流程：**先解决连接，再进入业务和方法访谈。
- **已有连接：**复核本次所需能力，沿用已知资料，不重复安装或推荐供应商。
- **只读分析：**读取足够就开展分析，不为报表要求发布权限。
- **缺少连接：**列出具体缺口；用户主动给出的资料可保留为当前任务输入，不能伪造连接快照。

工具、账户和用户授权是三件事。能调用修改接口，不等于已同意修改。

## 2. 理解业务与用户的方法

先读本次相关资料和用户已经确认的约定，整理一份短摘要：产品是什么、在哪个市场、Web 还是 App、怎样转化和变现、预算边界、数据来源，以及本轮要解决什么问题。

**新手示例：**“我有课程网站，但不知道怎么测素材。”Agent 可以提出两个候选：比较两个开头，或比较两种内容方向。解释固定项、变化项、观察指标和仍未知的条件，由用户选择。

**熟手示例：**“保留我的原组，另开一组测试，先别动存量。”Agent 把原组列为禁止修改对象，记录新组的变量和预算，再核对缺项。旧经验与这次方法冲突时，展示冲突，不悄悄替换用户的方法。

IAA、IAP、混合变现、购买、表单和有效线索等条件决定要补哪些信息；不知道长期收入时保留未知。不要把作者历史使用过的 1n1、预算阶梯或止损数字变成所有人的默认规则。

## 3. 准备一份能直接审阅的方案

从资料和当前状态出发，完成可逆的准备：核对目的地和转化事件、整理素材身份与规格、查重、列出可用与排除理由、准备原生配置、核算本轮预算。

素材选择要有依据。工具实际查看了画面或视频，就记录查看范围；只有文件名或制作说明，就说明判断依据。不要把模型推测写成已观看、已验证或效果最好。

整批审阅单至少包含：

- 产品、平台、账户、事件、市场、语言和目的地。
- 选用素材与文案、排除项、测试变量和固定项。
- 创建、修改、暂停、启用的具体对象；哪些现有对象保持原样。
- 币种、预算所属对象、日预算或总预算、排期与重叠花费。
- 与当前配置的差异、依赖和未解决项；部分完成时如何处理。
- 计划版本、需要用户确认的范围与执行后的验收方式。

例如：“保留原计划；新建两组，各用一个素材；总测试额度为用户给定值；先建立暂停对象并核对，再按本批确认范围启用。”创建暂停对象也是外部写入，必须包含在授权内。

## 4. 确认整批后，连续完成获准步骤

用户确认最终方案后，记录确认指向的版本、账户、对象、动作、预算和限制。范围内的机械步骤可以连续完成，无需每上传一条素材重新问一次；新增账户、增加费用、改变方法或扩大修改对象时，先给出更新后的具体差异。

执行前重新读取相关配置：

- 当前值已是目标值：核对后跳过重复修改。
- 当前值与准备方案时不同：保留差异，先查清背景，不推断是谁改的。
- 状态未知、字段缺失或工具超时：先查询已有对象和请求结果，再决定是否重试。

按依赖完成媒体处理、对象创建和字段配置。各平台保留自己的对象关系，不强迫 Google 等平台套用 Meta 的层级。记录每项请求与返回的对象标识；这些私有标识留在用户自己的任务目录。

## 5. 用实际读取结果写回执

**回执中的实际值必须来自对应操作后的工具结果。**计划里的目标值、脚本里的常量和模型的“已完成”文本，都不能填进实际结果列。

| 要回答的问题 | 所需证据 | 可以怎样表述 |
|---|---|---|
| 请求是否发出并被接收？ | 请求回执或平台操作记录 | 已提交；仍需查对象 |
| 配置是否符合计划？ | 同一对象的字段读回，含时间 | 配置已核对；指出不一致字段 |
| 审核状态是什么？ | 对象实际审核状态 | 审核中 / 被拒 / 已通过 / 未知 |
| 能否投放？ | 对象及父级的实际可投状态、限制信息 | 当前可投 / 受限；不等于有展示 |
| 有没有开始投放？ | 对应时间窗的展示或花费等数据 | 已观察到展示 / 花费；写明截至时间 |
| 效果是否改善？ | 可比且足够成熟的后续数据 | 观察结果与不确定性；不能由“已启用”推断 |

只记录拿得到的字段。不同平台不一定都有上述全部字段；缺失写未知，不补造成功状态。一批里 8 项成功、1 项审核中、1 项读取失败，要分别交接。

## 6. 下一轮先回验，再提出新动作

有相关上一轮待办时，先检查它们：建议有没有被采用、操作有没有生效、数据是否成熟。未执行的建议不能被评价为“执行后无效”；配置成功与效果改善分开记录。没有同一任务的历史，不加载无关产品资料。

完成本轮交接：**已确认结果、未完成项、下一步、需要用户决定的事**。日报可以另给一段便于转发的短文，但保留来源、账户覆盖、明细和口径差异。取数失败不等于零，旧文件不能冒充本轮实时数据。

用户纠正时，先修当前结论；用户明确要求保存后，再整理为带产品、适用条件、来源和版本的私有约定。新观察仍是候选，方法改版要更新相关计划。经验积累不是让 Agent 自行放宽预算、发布权限或平台要求。

## 其他人怎样复用

复制[任务记录模板](../templates/task-record.zh-CN.md)到自己的私有目录，让宿主按本页组织任务；业务资料、原生对象标识、回执和素材均留在本地。连接可换，方法可换，准备—确认—执行—核对的步骤继续复用。

在新宿主首次尝试时，先做一项读取或准备任务，再在明确授权范围内验证写入与读回。某个 WorkBuddy 历史案例不证明另一宿主已配置完成，也不证明三个平台所有广告产品都支持。

需要运行公开代码验证计划、恢复和数据检查时，使用[离线实验说明](capability-status.zh-CN.md#离线验证入口)。不要把模拟确认文件或示例账户用于真实操作。
